# Stage 4：分數校準與每日提醒量上限

本次完成三種分數轉換與每日 5%、10%、20% 提醒上限的離線比較，主方案預先固定為 **Sigmoid 校準＋每日 10% 上限**。在相同的 18,833 筆開發回測訂單中，主方案提醒 1,845 張，誤報 **1,493** 張、抓到延遲 **352** 張、漏掉 **1,290** 張，召回 **21.44%**。相較本輪相同校準方式的不限量方案，少了 5,430 張誤報，也少抓 656 張延遲。

每日上限確實控制了提醒量，但三組歷史政策驗證在 10% 上限下都無法達到召回至少 30%。實驗明確保留 `feasible=false`，採用上限優先的備援規則；不能把這個結果解讀為同時完成減少誤報與召回目標。既有預設模型與先前研究產物維持原狀，本輪另存研究 artifact。

所有數字來自 [calibration_budget.json](../reports/stage4/calibration_budget.json)。回測月份仍為已反覆檢視的 2017-12、2018-02、2018-04，合計 18,833 筆、1,642 張延遲訂單，訂單 ID 與 [每月重訓實驗](STAGE4_MONTHLY_RETRAINING.md)一致。原本 2018-05-26 起的保留期間沒有重新評分；本輪沒有新增獨立測試成績。

## 沿用模型，拆開校準與選政策的資料

本輪沒有重訓基礎模型，沿用前次八個月份、四個候選的 **32 份歷史版本**。執行時重新建構核准當下可得的特徵，核對原始資料 manifest、版本 artifact 的 SHA-256、切分資訊及既有 OOT 分數，確認可重現後才進入新實驗。四個候選仍為 RF／Static、Logistic／Static、RF／Route、Logistic／Route，分別使用既有 21 或 30 欄特徵。

基礎模型的訓練規則不變：對月份起點 `M`，訓練訂單核准時間嚴格早於 `M − 60 天`，送達標籤嚴格早於 `M`。各歷史月份使用當月版本留下的 out-of-time（OOT）分數。最後回測月 `E` 使用其自身月份模型，沒有用新模型重評舊訓練列來取代歷史驗證分數。

在 `E` 時點，把既有三個歷史月拆成前兩月校準、第三月政策驗證，兩部分訂單不重疊：

| 決策／開發回測月 E | 校準 OOT 月份 | 已知校準標籤／其中延遲 | 政策驗證 OOT 月 | 完整政策評分筆數 | 已知政策標籤／其中延遲 | 當時仍未知的政策標籤 |
| --- | --- | ---: | --- | ---: | ---: | ---: |
| 2017-12 | 2017-07、08 | 8,043／227 | 2017-09 | 4,162 | 4,159／180 | 3 |
| 2018-02 | 2017-09、10 | 8,601／365 | 2017-11 | 7,149 | 7,137／862 | 12 |
| 2018-04 | 2017-10、11 | 11,587／1,055 | 2017-12 | 5,675 | 5,671／442 | 4 |

校準 fit 只使用前兩月、且送達標籤嚴格早於 `E` 的訂單。第三個月保留完整評分 cohort，但只有標籤嚴格早於 `E` 的列可以計算召回、FP、TP 與選門檻；未成熟列不被當成準時，也不從每日容量或排名中刪掉。

校準器與政策都在 `E` 才 fit／選定。第三個月的機率指標是對校準 fit 資料以外的歷史資料評分，但不能聲稱當時第三個月月初已部署這個校準器。所有門檻、候選與備援選擇固定後，才讀取 `E` 當月的結果計算開發回測成績。

最終 `E` 模型可以使用當時已成熟的舊校準／政策訂單訓練；本輪用於校準與選政策的分數，仍來自這些訂單原本月份尚未訓練過它們的模型版本。後續 fold 可使用更早回測月的資料，例如 2017-12 成為 2018-04 的政策月，三組因此不是互相獨立的測試。

## 三種校準方式與機率指標

| 方法 | fit 與轉換方式 | 同分及外插處理 |
| --- | --- | --- |
| `raw` | 原始分數，不 fit 轉換參數 | 原樣保留 |
| `sigmoid`，預先指定主方案 | 原始分數先裁切至 `[1e-6, 1−1e-6]` 並取 logit，再 fit 無類別加權的 Logistic Regression；`C=1e6`、`max_iter=2000`、`tol=1e-10` | 若擬合斜率非正，改用校準期延遲比例常數，避免反轉排名；本輪 12 組 Sigmoid fit 均未觸發此備援 |
| `isotonic` | 無類別加權、單調不減的 Isotonic Regression | 超出校準分數範圍時裁切，可能產生同分平台 |

總共實際 fit **24 個校準器**，即三組回測、四個候選、兩種有學習參數的校準方法。每個候選與每種轉換共用相同基礎分數，四種提醒預算不另外訓練。

## 每日上限、門檻與不可行時的處理

預算 `p` 對每天完整評分 cohort 套用 `K = floor(p × 當日筆數)`，沒有跨日借用額度。主方案 `p=0.10`，另比較 0.05、0.20 與不限量。取整使用十進位運算，避免浮點誤差把例如 `0.29 × 100` 誤算成 28；小批次可能得到零個名額。

先依「校準分數由高到低、原始分數由高到低、order_id 由小到大」排出當日 top-K，再以 `校準分數 >= 門檻` 篩選。這與在達門檻列中保留最多 K 張等價。Isotonic 平台內保留原始分數的排序，最終同分用訂單 ID 決定，輸入列順序不會改變結果。

政策驗證中，門檻選擇以**完整批次提醒筆數最少**為目標，條件是已知標籤召回至少 30% 且符合每日上限。校準分數同分的門檻群組不可拆開。未成熟訂單保留排名與容量競爭，但其結果不進入召回、FP、TP 或 precision 計算。報告把完整提醒數、已知標籤提醒數、未知標籤提醒數分開保存。

若 top-K 全部提醒仍抓不到 30% 已知延遲，該候選記錄 `feasible=false`，門檻設為零，取得這個上限與排名下可達的最高召回。這裡的「最高」只限於既定排名加單一門檻規則，不代表所有可能模型或任意訂單集合的最佳結果。

每個校準方法與預算分別選候選。先從可行候選中選完整提醒數最少者，再依已知 FP、原始分數 Average Precision、固定候選順序決勝。若四個候選全部不可行，選已知召回最高者，再依已知 FP、完整提醒數、原始 AP、固定順序決勝。候選選擇不讀取開發回測結果。

此規則需等一天結束、取得完整批次後排名，核准後最長約等待一天，適合日結提醒。它不是即時單筆預測，也不是用月底整月排名模擬每日服務。程式可檢查日期、唯一訂單 ID 與容量，無法單憑 CSV 證明外部系統已提供完整一天；完整性仍是呼叫端必須履行的契約。

## 重現與研究 artifact

沿用專案 `.venv`、本機 Olist CSV、前次每月重訓的模型快取與分數表，不需要 MySQL 或新增套件。缺少歷史版本時先完成前次滾動實驗；校準腳本會檢查來源與快取是否一致，不會直接相信檔名。

```powershell
.\.venv\Scripts\python.exe scripts\compare_calibration_budget.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

要以 2018-04 主方案研究 artifact 重播完整開發月，先從原始資料建立同一有效完成 cohort 的特徵批次：

```powershell
@'
from pathlib import Path
import pandas as pd
from scripts.delay_route_features import build_route_delay_dataset
features = build_route_delay_dataset(Path('data/raw/olist'))
mask = features.prediction_time.ge(pd.Timestamp('2018-04-01')) & features.prediction_time.lt(pd.Timestamp('2018-05-01'))
Path('.runtime').mkdir(exist_ok=True)
features.loc[mask].to_csv('.runtime/calibration_budget_2018-04_features.csv', index=False)
'@ | .\.venv\Scripts\python.exe -

.\.venv\Scripts\python.exe scripts\predict_delay.py --model models\research\olist_delay_calibrated_budget_2018-04.joblib --features-csv .runtime\calibration_budget_2018-04_features.csv --complete-daily-batches --output .runtime\calibration_budget_2018-04_replay.csv
```

`--complete-daily-batches` 是呼叫端對完整日結批次的明確聲明，程式不會據此驗證外部來源完整。限量 artifact 拒絕 `--order-id` 單筆模式，也拒絕未聲明完整批次的 CSV。輸出保留 `raw_delay_score`、校準後 `delay_score`、門檻、`threshold_eligible`、`budget_suppressed` 及最終 `predicted_delayed`；提醒數必須看最終決策，不能只用 `delay_score >= threshold` 重算。

特徵 CSV 可以含標籤等額外欄位，推論只取保存的特徵白名單，不使用那些結果。每份最終 artifact 只對應其開發月模型；用它重評早期訓練訂單不能當成 OOT 成績。舊版沒有校準器或上限的 artifact 仍沿用原本推論契約。

獨立核對 768,600 列分數、重擬 24 個校準器、144 組政策、288 組每日容量、108 組機率指標及 6 組常數基準、60 列摘要、全部 256,124 列舊分數，以及三份研究模型重載推論。原分數與 Sigmoid 的 96 組政策／回測提醒向量完全一致。圖表完成視覺檢查；65 份既有模型、報告與圖表 SHA-256 不變。驗證腳本與執行證明保存在 Git 忽略的 `.runtime/verification/`。

## 限制與後續方向

這是「有效、最終已送達且可建立標籤」cohort 的歷史重播。每日分母包含這份 cohort 內未成熟結果的訂單，仍沒有涵蓋所有原始核准訂單；取消、未完成及無法建立有效日期的訂單不在本次容量分母內。這個分母在真實核准當下未必可識別，直接上線前需先定義實際所有可評分訂單的範圍、結果追蹤與完整批次檢查。

已知標籤可能偏向較快完成的訂單，即使等待至少 60 天，仍不能把已知子集召回當成全體即時可知成績。不同月份的分數來自不同模型版本；一個用舊版本 fit 的單調校準器，不能保證新版本機率仍校準。尤其本輪 RF／Route 在 2018-04 雖優於原始分數，仍輸給常數基準。

目前已能控制每日提醒工作量，尚未同時達成 10% 上限與歷史召回至少 30%。下一步可先固定可接受的漏報成本與最低召回，再檢查排序能力及哪些路線、承諾區間在 top-K 以外累積漏報；若要比較新的模型、特徵或版本專屬校準規則，應先固定選擇方式，再取得未參與方法調整的新期間評估。這些開發數字不構成提升研究 artifact 為預設模型的依據。
