# Stage 4：相同堆積特徵，比較分類與每日排序

本輪固定原 XGBoost 地理 83 欄、加入 7＋14 天逾期堆積的 101 欄，成對比較「預測每張訂單是否延遲」與「學習把當日延遲訂單排前面」兩種訓練目標。完成 **16 次新 fit**，每日提醒上限維持 10%。正式結果見[實驗報告](../reports/stage4/backlog_objectives.json)與[訓練前規格](../reports/stage4/backlog_objectives_specification.json)。

結果沒有形成穩定改善：83 欄排序在三個開發月合計多抓 8 張延遲，101 欄排序反而少抓 3 張。兩個排序模型在七月改善、九月退步，全部 67 候選的歷史選模也沒有選到新排序模型；**主方案仍為 TP 418、FP 1,427、FN 1,224，開發召回 25.46%、最差歷史召回 19.17%**。

## 為什麼比較訓練目標

前一步[七、九月提醒名額診斷](STAGE4_BACKLOG_ROUTE_EXCHANGES.md)發現，加入堆積特徵後新增的 22 張漏報，有 20 張仍在當日 10–20% 排名。這提供了檢查前段排名的方向，但不代表改用排序目標就一定能把這些訂單送進前 10%。先前已用 45／60 欄試過 LightGBM LambdaRank，本輪是不同特徵組的 XGBoost 分類／排序配對。

分類模型對每張訂單學習準時／延遲；本輪排序模型把同一天的訓練訂單當一組，在組內學習延遲件與準時件的順序。兩者評分後都依相同每日 10% 規則挑提醒，不為特定路線加保留名額。

## 固定配對與時間規則

| 特徵包 | 分類候選，重播既有模型 | 每日排序候選，新訓練 |
| --- | --- | --- |
| 原地理／負載交互，共 83 欄 | `xgboost_engineering_geo` | `xgboost_rank_geo` |
| 同上加 7＋14 天堆積，共 101 欄 | `xgboost_backlog_7_14d` | `xgboost_rank_backlog_7_14d` |

沒有新增、重算或挑選特徵。各配對使用相同訓練訂單、列順序、缺值處理與類別編碼；補值與編碼僅在 train fit。原始特徵 CSV 包含其他研究欄位，但模型只讀 artifact 的 83／101 欄白名單，答案、實際送達時間與 ID 不作模型特徵。

核心樹參數配對固定為 400 棵、學習率 0.05、深度 4、`min_child_weight=10`、行／欄取樣 0.8、L2 10、`hist`、seed 42；分類為 `binary:logistic`，排序為 `rank:ndcg`，另使用排序所需設定。沒有超參數搜尋、開發 `eval_set` 或 early stopping。

排序依核准日建立連續 query group，固定 `lambdarank_pair_method=topk`、`lambdarank_num_pair_per_sample=20`、`ndcg_exp_gain=False`，記錄 `ndcg@20`。成熟訓練列中全準時或全延遲的日期仍保留，但沒有異類配對；各月有 188–461 個訓練日期，並非每組都有有效的正負配對。

[XGBoost 官方排序文件](https://xgboost.readthedocs.io/en/stable/tutorials/learning_to_rank.html)說明如何按 query 分組、以 `rank:ndcg` 與 `topk` 建立訓練配對。本輪用日期作 query；**固定前 20 名的訓練焦點，不等於每個日期隨訂單量變動的 10% 切點**，也沒有每月召回 30% 的保證。

排序 margin 經嚴格單調 sigmoid 轉成既有推論介面的有界分數，若不同 margin 被壓成同分則拒絕。這不是另行 fit 的機率校準，`delay_score=0.8` 不能解讀成 80% 延遲機率。

- 每月訓練依 `deadline_wait0`：核准與 `min(實際送達時間, 承諾日次日午夜)` 都須嚴格早於模型月初，無額外核准等待。實際送達欄位保持原值。
- 八個模型月份為 2017-07、08、09、10、11、12、2018-02、04；兩種新排序各訓練八份，共 16 fit。16 次均無 fit warnings。
- 每個歷史月份使用該月自己的模型，歷史答案只用選模截止前實際已送達者，不能用後續結果提前補成已知。
- 提醒先對完整日批次排序，再遮蔽未知結果計指標；未知訂單仍競爭名額，不能當準時或從每日容量計算的完整母體移除。指標分母僅使用已知結果。每日容量為 `floor(0.10 × 完整當日筆數)`，無跨日借額。
- 三歷史月最低召回優先，其次歷史合計 TP、原始 AP、固定候選順序選模；30% 是適用判定，不以開發成績回頭改選。

兩個排序模型各自補抓原 22 張中的 9 張，並不代表這 9 張是同一批，也不能合併兩個提醒名單當成符合 10% 預算的方案。101 欄排序把七月 SP→SP 原先漏掉的 5 張補回 4 張，九月 SP→BA 的 6 張只補回 2 張。

## 歷史選模與主方案

四候選限定組、兩分類限定組、兩排序限定組及完整主方案，都是規格先固定後依相同歷史規則選擇；不依上表開發最高分改選。

| 預先指定選組 | 合計 TP | 開發召回 | 最差歷史召回 | 說明 |
| --- | ---: | ---: | ---: | --- |
| 兩分類候選 | 300 | 18.27% | 15.61% | 三 fold 選 83／101／101 欄分類 |

主方案在十二月選原 XGBoost 83 欄、二月選 Logistic C=0.01 加 14 天堆積、四月選 Logistic C=0.01 加近期核准量 trend。三個 fold 都未通過每個歷史月至少召回 30% 的要求，主方案 FP／FN 與提醒集合保持前輪結果。

## 重用與來源追溯

本輪凍結前輪[65 候選報告](../reports/stage4/backlog_changes.json)、完整特徵、分數 CSV、七份來源 CSV 的 SHA-256。報告、規格與每份模型都保留來源、切分、特徵白名單與參數；來源不符就停止。

本輪實際重播兩個分類候選的八個月份版本，共 **16 份既有分類模型**，核對舊分數後與 16 份新排序模型配對。其餘 63 舊候選／504 月份模型的指標從 SHA 綁定的前輪報告原值重用，**本輪沒有重新評分這 504 份模型**。完整主方案是在舊 65 候選加兩個新候選間選模，不能把 67 候選都寫成新訓練或全數重播。

本輪分數 CSV 只匯出四配對候選，共 **256,224 列**；其中同月份可能在不同 fold 出現，列數不是獨立訂單數。新月份模型在 `models/research/objective_versions/`，主方案 artifact 為 `models/research/olist_delay_objective_YYYY-MM.joblib`，資料、模型、逐筆分數與執行證據都由 Git 忽略。

診斷另核對來源與 32 份模型雜湊，從本輪分數帳本驗證全部 256,224 列、12 個 phase 與 24 組目標配對，指標及完整日批次逐項對齊正式報告；該診斷指令本身 **0 次 fit、0 次模型反序列化／重播、沒有重新選模**。`historical_validation` 與 `development_retest` 分開記錄，避免混用答案可見時間。

## 重現與完整日批次推論

需先建立前輪堆積特徵、分數與分類月份模型，GitHub 不含本機原始資料與模型。以下指令不需啟動 MySQL，也不需新增 Python 套件。

```powershell
.\.venv\Scripts\python.exe scripts\compare_backlog_objectives.py --specification-only --n-jobs 2
.\.venv\Scripts\python.exe scripts\compare_backlog_objectives.py --n-jobs 2
.\.venv\Scripts\python.exe scripts\diagnose_objective_misses.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

僅重播已產生的本輪排序版本可加 `--reuse-new-versions`，程式會檢查模型綁定的規格雜湊、來源、切分與特徵一致，不會把任意既有模型當成本輪結果；實際參數與擬合狀態另經本輪獨立核對。

以下依主方案 artifact 白名單產生相同完整四月研究批次，不含答案欄位；類別讀為 `object`，保留 ZIP 前導零：

```powershell
@'
from pathlib import Path
import joblib
import pandas as pd
artifact = joblib.load('models/research/olist_delay_objective_2018-04.joblib')
features = pd.read_csv('data/processed/olist_delay_backlog_features.csv',
    float_precision='round_trip', dtype={c: object for c in artifact['categorical_features']})
month = pd.to_datetime(features.prediction_time).dt.strftime('%Y-%m')
columns = ['order_id', 'prediction_time'] + artifact['feature_names']
Path('.runtime/verification').mkdir(parents=True, exist_ok=True)
features.loc[month.eq('2018-04'), columns].to_csv(
    '.runtime/verification/objective_april_batch.csv', index=False)
'@ | .\.venv\Scripts\python.exe -
.\.venv\Scripts\python.exe scripts\predict_delay.py --model models\research\olist_delay_objective_2018-04.joblib --features-csv .runtime\verification\objective_april_batch.csv --complete-daily-batches --output .runtime\verification\objective_april_predictions.csv
```

主方案可能選到舊分類器，應以 artifact 的實際候選、欄位與政策解讀，不假設它是新排序模型。完整批次由呼叫端保證；程式不能從片段 CSV 證明沒有漏單。政策需要完整、已結束的日曆日批次，最多等待一天，不能解讀為單筆即時提醒上限。
