# 專案從起始到目前的進度

資料環境、SQL與商業分析初版已完成；Stage 4仍待資料、每日10%與五種子維持，Stage 5仍待資料並保留兩臂研究交付。Stage 6最新準備真實G2的來源、完整同ID、輸出及反讀契約，57來源與既有G1／G2證據同版，完整流程先以合成資料驗接線。本輪真實只核metadata／hash，未解析CSV、估真實切點、產生真實tuple、分群、訓練或Dashboard；G3、跨時間及營運用途仍未驗收。

這個專案想完成的完整流程是：讀懂電商資料 → 建立資料庫 → 找出商業現象 → 預測與推薦 → 透過 API、前端與 Dashboard 展示。目前完成的是前半段，延遲模型仍在研究驗證。

## Stage 4 為什麼做了這麼多輪

我們希望在訂單核准時，就挑出可能晚於承諾日期送達的訂單。現在的使用情境是：**每天完整批次最多提醒 10% 訂單，盡可能抓到真正延遲的訂單。** 每天各自取整，不借用其他日期的名額。

「召回率」表示所有實際延遲訂單中，有多少被提醒；「誤報」是提醒了最後仍準時的訂單；「漏報」是實際延遲卻沒提醒的訂單。提醒名額固定後，多抓一張延遲通常代表少占用一個準時訂單的名額。因此後期的重點是改善前 10% 排名，同時檢查不同月份與路線的得失。

| 順序 | 做了什麼、為什麼做 | 實際發現與限制 |
| --- | --- | --- |
| 1. 第一版延遲模型 | 建立每訂單一列、21 個核准時可用特徵；用時間順序分訓練／驗證／保留測試，選出 Random Forest | 原版保留測試抓到 155／672 張延遲，但誤報 2,571 張，成為可重現的起點；品質仍不足。見[第一版方法](STAGE4_DELAY_PREDICTION.md) |
| 2. 多模型比較 | 相同 21 欄比較 Logistic、RF、Extra Trees、HistGradientBoosting、XGBoost、LightGBM | Logistic 的三個開發月平均 AP 最高；更複雜的樹模型沒有穩定勝出。AP 是排序指標，不能直接當成 accuracy 或固定預算召回。見[多模型比較](STAGE4_DELAY_PREDICTION.md#多模型時間回測) |

## 結果的適用範圍

上述三個開發月已被多次用來檢視和設計下一輪實驗，不能當成未知新資料成績。原版 2018-05-26 起保留測試的召回 23.07% 使用另一個期間、模型與提醒規則，**不能拿它與本表的 25.15% 直接比較**；後續固定預算研究沒有重新評分該保留期間。

目前預設推論仍用原版 Random Forest。研究流程可以在不同月份依歷史資料選到 XGBoost 或 Logistic，研究成績改善不會自動替換預設模型。當前標籤母體仍是時間合理且最終已送達的訂單；待件情境雖納入其他有效核准訂單，不能據此宣稱已驗證所有核准、取消與未送達訂單。
