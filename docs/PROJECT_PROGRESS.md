## Stage 4 為什麼做了這麼多輪

我們希望在訂單核准時，就挑出可能晚於承諾日期送達的訂單。現在的使用情境是：**每天完整批次最多提醒 10% 訂單，盡可能抓到真正延遲的訂單。** 每天各自取整，不借用其他日期的名額。

「召回率」表示所有實際延遲訂單中，有多少被提醒；「誤報」是提醒了最後仍準時的訂單；「漏報」是實際延遲卻沒提醒的訂單。提醒名額固定後，多抓一張延遲通常代表少占用一個準時訂單的名額。因此後期的重點是改善前 10% 排名，同時檢查不同月份與路線的得失。

| 順序 | 做了什麼、為什麼做 | 實際發現與限制 |
| --- | --- | --- |
| 1. 第一版延遲模型 | 建立每訂單一列、21 個核准時可用特徵；用時間順序分訓練／驗證／保留測試，選出 Random Forest | 原版保留測試抓到 155／672 張延遲，但誤報 2,571 張，成為可重現的起點；品質仍不足。見[第一版方法](STAGE4_DELAY_PREDICTION.md) |
| 2. 多模型比較 | 相同 21 欄比較 Logistic、RF、Extra Trees、HistGradientBoosting、XGBoost、LightGBM | Logistic 的三個開發月平均 AP 最高；更複雜的樹模型沒有穩定勝出。AP 是排序指標，不能直接當成 accuracy 或固定預算召回。見[多模型比較](STAGE4_DELAY_PREDICTION.md#多模型時間回測) |
| 3. 減少誤報 | 依使用者指定，在驗證至少召回 30% 的條件下，調門檻並測試近 90 天配送歷史 | 原版保留期間的回溯診斷少 170 張誤報，也少抓 3 張延遲；新增歷史特徵未勝出。這是已檢視資料的診斷，沒有產生新的獨立測試。見[平衡模式](STAGE4_ALERT_OPTIMIZATION.md) |
| 4. 月份落差診斷 | 拆開月份、州別、路線、承諾天數與資料成熟度，找出誤報集中的情況 | 發現平均成績掩蓋弱月份，且只保留已送達答案會特別排掉慢件。見[月份診斷](STAGE4_MONTHLY_DIAGNOSTICS.md) |
| 5. 等待期與路線承諾 | 比較 30／60 天等待，讓慢件有時間取得結果；加入路線歷史配送與承諾餘裕 | 延長等待改善慢件答案保留，但犧牲資料新鮮度；路線特徵有局部增益，月份崩落仍存在。見[等待期實驗](STAGE4_WAITING_EXPERIMENT.md) |
| 6. 多月份驗證 | 比較只看最新月、合併三月、每月召回下限，避免一個好月份蓋過弱月份 | 歷史驗證每月達到 30%，仍不能保證後續開發月達標；提醒量增加也不等於泛化能力提高。見[多月份驗證](STAGE4_MULTIMONTH_VALIDATION.md) |
| 7. 每月重訓 | 改成歷史各月與開發各月都用當時資料重訓，避免一直用舊模型 | 能多抓延遲，但也多出誤報；不同月份模型的分數尺度不同，共用門檻難以穩定轉移。見[滾動驗證](STAGE4_MONTHLY_RETRAINING.md) |
| 8. 分數校準與提醒上限 | 比較原始分數、Sigmoid、Isotonic，以及每日 5%／10%／20% 預算；主方案固定 10% | 控制了提醒量，也明顯犧牲召回。固定 10% 主方案開發召回為 21.44%；校準本身沒有讓這批每日提醒排序改善。見[校準與預算](STAGE4_CALIBRATION_BUDGET.md) |
| 9. 固定預算排名特徵 | 分析漏報路線與承諾天數，擴充賣家、路線、ZIP3 等資訊並比較提升樹與加權分類 | 主方案仍為 21.44%，新特徵沒有讓歷史選定結果改善。見[第一輪排名實驗](STAGE4_BUDGET_RANKING.md) |
| 10. 未完成件與每日排序 | 加入尚未觀測到送達的件數、等待天數與逾期件數；初次比較 LambdaRank 每日排序 | 主方案仍為 21.44%，當時的排序限定組合也未勝出；這不代表所有特徵下的排序目標都無效。見[待件與排序](STAGE4_PENDING_RANKING.md) |
| 11. 更早可知的訓練答案 | 到承諾日結束仍未送達，就能知道它會延遲；比較訓練答案時鐘與等待期 | 主方案多抓 6 張，開發召回到 21.80%；歷史驗證仍只用選模當時已送達的結果，沒有把未知答案當準時。見[答案時鐘](STAGE4_OUTCOME_CLOCK.md) |
| 12. 地理與負載交互 | 加入距離與地理參考、待件壓力比例，再將地理與負載分開測試 | 地理組沒有穩定增益；只加負載的 Logistic 出現小幅改善訊號。主方案到 21.86%，拆組後沒有再增加。見[特徵工程](STAGE4_FEATURE_ENGINEERING.md)與[分組消融](STAGE4_FEATURE_ABLATION.md) |
| 13. Logistic 正則化 | 固定 65 欄負載特徵，只比較正則化強度，避免同時改特徵 | 主方案到 25.58%，是這段研究較大的改善；強正則化仍未讓所有歷史月份穩定，沒有按開發最高分事後改選。見[正則化比較](STAGE4_LOGISTIC_REGULARIZATION.md) |
| 14. 十二月及歷史漏報 | 重播既有模型，檢查長承諾、SP→RJ、完整日排名與模型共同漏掉的訂單 | 找到長承諾與特定路線弱點；模型補抓一些延遲時，也會在其他路線新增漏報。這步只診斷，沒有新訓練。見[十二月漏報](STAGE4_DECEMBER_MISS_DIAGNOSTICS.md) |
| 15. 路線 × 承諾 × 近期負載 | 加入近 7／14 天核准量變化與明確交互，測試壓力是否因路線、承諾而異 | 局部月份改善，整體不一致；主方案少抓 3 張，回到 25.40%。見[路線負載交互](STAGE4_ROUTE_LOAD_INTERACTIONS.md) |
| 16. 逾期未送達堆積變化 | 分開測試 7 天、14 天與兩者合併的逾期待件歷史量、增減與成長 | XGBoost 固定候選在開發月份改善，但七、九月退步；歷史選定主方案只多抓 1 張，到 25.46%。見[堆積變化](STAGE4_BACKLOG_CHANGES.md) |

## 這些結果代表什麼

上述三個開發月已被多次用來檢視和設計下一輪實驗，不能當成未知新資料成績。原版 2018-05-26 起保留測試的召回 23.07% 使用另一個期間、模型與提醒規則，**不能拿它與本表的 25.15% 直接比較**；後續固定預算研究沒有重新評分該保留期間。

目前預設推論仍用原版 Random Forest。研究流程可以在不同月份依歷史資料選到 XGBoost 或 Logistic，研究成績改善不會自動替換預設模型。當前標籤母體仍是時間合理且最終已送達的訂單；待件情境雖納入其他有效核准訂單，不能據此宣稱已驗證所有核准、取消與未送達訂單。

本輪固定模型與既有分數，診斷固定 k 如何與每日訂單量交互。101 欄 k＝20 → 10，七月多抓 3 張，十二月少抓 3 張；十二月純 k 的損失落在低量與唯一 400+ 日，200–399 組反而多抓 1 張。主方案由 83 欄分類改為 101 欄排序的 −5，則在 200–399 組少抓 9 張，同時涉及特徵、目標與 L2，不能寫成同一個 k 效果。

固定 k＝10 只在七月 4／31 天、十二月 2／31 天等於實際 10% 容量。訓練 query 是當時依答案時鐘可用的成熟子集，並非完整日母體；同一 k＝10 的名義位置覆蓋在七月 13.66%、十二月 9.79%，更接近 10% 也沒有保證固定候選改善。這些是對帳與關聯描述，沒有證明切點差距造成退步；少日期、小路線的增減也不能視為穩定效果。

本輪診斷 CLI 完成 512,448 列來源帳本、12 個 phase 與 70 個來源／模型雜湊核對，分析兩個 phase、九組比較，0 次 fit、0 次模型重播、0 次選模。聚合報告見 [rank_batch_size_diagnostics.json](../reports/stage4/rank_batch_size_diagnostics.json)，逐筆分數與本機模型仍由 Git 忽略。

406 項測試、31 個 Notebook 程式區塊通過；獨立核對 96 組來源指標、62 個完整日批次、九組比較與 142,884 個群組欄位。訓練 query 的 531 個過去有效日期也逐日核對，七月 189、十二月 342，其中各一天沒有成熟訓練列。

這次結果不支持只因容量不吻合就擴大固定 k 搜尋。下一次建議固定 101 欄、L2＝100、配對參數整數 10 與其他設定，只比較 `lambdarank_pair_method=topk → mean`，同時檢查七、九月和十二月。`mean` 的 10 代表每列取樣配對數，並非固定前 10 名或動態 10%，內部正規化也會隨 method 變化；這是研究假設，不能保證回收漏報。本輪沒有追加訓練；研究模型仍需另行安排未參與調整的新期間驗證，之後才討論 Dashboard 與下一階段。
