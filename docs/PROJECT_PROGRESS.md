# 專案從起始到目前的進度

這個專案想完成的完整流程是：讀懂電商資料 → 建立資料庫 → 找出商業現象 → 預測與顧客分析 → 推薦 → 透過 API、前端與 Dashboard 展示。目前完成的是前半段：資料環境、SQL 與 EDA 初版完成；延遲預測與評論低評分預測已整理成離線研究交付，正式適用待新資料；RFM 已完成真實資料集與描述，分群切點尚未對真實資料執行。

本頁每一輪只留一列摘要，完整方法、數字與驗證寫在各輪文件；首頁只摘要目前結果。三個研究反覆使用的 2017-12、2018-02、2018-04 是已檢視的開發回測月份，不能當成未知資料成績。

## Stage 4 為什麼做了這麼多輪

我們希望在訂單核准時，就挑出可能晚於承諾日期送達的訂單。現在的使用情境是：**每天完整批次最多提醒 10% 訂單，盡可能抓到真正延遲的訂單。** 每天各自取整，不借用其他日期的名額。

「召回率」表示所有實際延遲訂單中，有多少被提醒；「誤報」是提醒了最後仍準時的訂單；「漏報」是實際延遲卻沒提醒的訂單。提醒名額固定後，多抓一張延遲通常代表少占用一個準時訂單的名額。因此後期的重點是改善前 10% 排名，同時檢查不同月份與路線的得失。

| 順序 | 做了什麼、為什麼做 | 實際發現與限制 |
| --- | --- | --- |
| 1. 第一版延遲模型 | 建立每訂單一列、21 個核准時可用特徵；用時間順序分訓練／驗證／保留測試，選出 Random Forest | 原版保留測試抓到 155／672 張延遲，但誤報 2,571 張，成為可重現的起點；品質仍不足。見[第一版方法](STAGE4_DELAY_PREDICTION.md) |
| 2. 多模型比較 | 相同 21 欄比較 Logistic、RF、Extra Trees、HistGradientBoosting、XGBoost、LightGBM | Logistic 的三個開發月平均 AP 最高；更複雜的樹模型沒有穩定勝出。AP 是排序指標，不能直接當成 accuracy 或固定預算召回。見[多模型比較](STAGE4_DELAY_PREDICTION.md#多模型時間回測) |
| 3. 減少誤報 | 依使用者指定，在驗證至少召回 30% 的條件下，調門檻並測試近 90 天配送歷史 | 原版保留期間的回溯診斷少 170 張誤報，也少抓 3 張延遲；新增歷史特徵未勝出。這是已檢視資料的診斷，沒有產生新的獨立測試。見[平衡模式](STAGE4_ALERT_OPTIMIZATION.md) |
| 4. 月份落差診斷 | 拆開月份、州別、路線、承諾天數與資料成熟度，找出誤報集中的情況 | 發現平均成績掩蓋弱月份，且只保留已送達答案會特別排掉慢件。見[月份診斷](STAGE4_MONTHLY_DIAGNOSTICS.md) |
| 5. 等待期與路線承諾 | 比較 30／60 天等待，讓慢件有時間取得結果；加入路線歷史配送與承諾餘裕 | 延長等待改善慢件答案保留，但犧牲資料新鮮度；路線特徵有局部增益，月份崩落仍存在。見[等待期實驗](STAGE4_WAITING_EXPERIMENT.md) |
| 6. 多月份驗證 | 比較只看最新月、合併三月、每月召回下限，避免一個好月份蓋過弱月份 | 歷史驗證每月達到 30%，仍不能保證後續開發月達標；提醒量增加也不等於泛化能力提高。見[多月份驗證](STAGE4_MULTIMONTH_VALIDATION.md) |
| 7. 每月重訓 | 改成歷史各月與開發各月都用當時資料重訓，避免一直用舊模型 | 能多抓延遲，但也多出誤報；不同月份模型的分數尺度不同，共用門檻難以穩定轉移。見[滾動驗證](STAGE4_MONTHLY_RETRAINING.md) |
| 8. 分數校準與提醒上限 | 比較原始分數、Sigmoid、Isotonic，以及每日 5%／10%／20% 預算；主方案固定 10% | 控制了提醒量，也明顯犧牲召回。固定 10% 主方案開發召回為 21.44%；校準本身沒有讓這批每日提醒排序改善。見[校準與預算](STAGE4_CALIBRATION_BUDGET.md) |
| 9. 固定預算排名特徵 | 分析漏報路線與承諾天數，擴充賣家、路線、ZIP3 等資訊並比較提升樹與加權分類 | 主方案仍為 21.44%，新特徵沒有讓歷史選定結果改善。見[第一輪排名實驗](STAGE4_BUDGET_RANKING.md) |
