# Stage 12：固定七筆的 SQL 與 append 波動診斷

本輪沿用 V19 的同一批 7 筆與原固定對照，釐清正重疊鄰居查詢及 append 耗時波動，同步記錄系統負載。這是已曝光 validation 的工程診斷；不新增身分，不修改排名方法，不執行完整 validation 或保留測試。

## 既有證據盤點

盤點前後核對 **116 份來源**、每次 **11,671,072 bytes**。核對 V19 七筆身分與順序、三輪工作量及帳本證據，保留原封存的七路資料抽取，不重選或重新掃描大型原始資料。本階段真實排名為 0。

V19 原有 21 次觀測各保留完整計時。下表是同一查詢三輪的範圍（最大減最小），不是本輪新測結果。單位毫秒。

| 鄰居數 | 原選法 | 正重疊鄰居整段變幅 | append 扣 commit／budget 變幅 | 核心變幅 |
| --- | --- | ---: | ---: | ---: |
| 1,945 | anchor | 6.185 | 0.096 | 13.120 |
| 1,958 | hash | 9.470 | 0.223 | 12.699 |
| 2,499 | segment_max | 3.616 | 0.905 | 11.620 |
| 2,770 | hash | 3.004 | 0.039 | 2.601 |
| 2,992 | segment_max | 0.606 | 0.345 | 14.759 |
| 3,156 | hash | 1.333 | 0.862 | 16.123 |
| 4,071 | segment_max | 22.917 | 6.307 | 30.678 |

原 `sql_positive_overlaps` 含 SQLite execute、逐列 cursor 取回與轉換、watch 呼叫、資料檢查及 Python 鄰居池組裝，因此不能把整段叫成純 SQL 引擎成本。原紀錄尚無 execute／取列分項與執行緒 CPU 時間。

最大同查詢核心變幅仍是 4,071 位鄰居案例，第 2→3 輪增加 **30.678 ms**。其中 append 增加 **6.307 ms**，既有分項已顯示主要為 **budget_check_other +6.253 ms**，payload write 僅 **+0.001 ms**，直接 budget 保存與 chunk commit 差值均為 0。因此下一步須區分預算檔讀取、JSON 解析及其餘檢查，不能先認定資料列寫入是原因。

V6 的 frame_encode 是外框序列化與 UTF-8 編碼；完整 expected／precise／delta_hex payload 已在 verify 階段建立。兩者分開解讀。系統負載只提供整輪背景，不能以三輪資料建立短查詢或 Ollama 的因果歸因。

## 固定範圍與後續

仍為 **55／55 格、170 個可比較查詢、232 個歷史身分**；`1101/n5/v4` 保持 11 個可比較查詢，其中高於 1,945 位鄰居的尾端為 6 筆。這輪所有重測皆為舊身分，不增加覆蓋。後續封存原方法與診斷方法交錯的循序窗口，核對全部七筆 V19 完整 payload，保留原對照與所有輪次，另觀察新增計時的擾動。
