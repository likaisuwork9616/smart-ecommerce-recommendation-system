# Stage 5：凍結分數與四欄支援診斷

後續已凍結[只移除購買月份的消融規格](STAGE5_REVIEW_MONTH_ABLATION_SPEC.md)，並核對原完整角色；尚未實作三欄模型或追加訓練。以下保留本輪診斷的來源、數字與假說形成過程。

本輪只讀[離線最小基線](STAGE5_REVIEW_OFFLINE_BASELINE.md)留下的分數，對照原H60角色名冊與購買／核准時鐘。完成各角色低評率、分數分布、四欄訓練／查詢支援及既有外層機率損失分解；**沒有新增fit、transform、predict、選C、門檻或模型效能結論**。

主要發現是購買月份在部分fit的合格歷史中幾乎沒有支援，而三個外層月的低評率與平均分數方向也不一致。下一輪建議只預先規劃「移除購買月份」消融，先不實作或訓練；它尚不能解釋全部誤差或保證改善。Stage 4繼續待資料，每日10%與11／29／42／73／101五種子不變，Dashboard暫緩。

## 單因子決策與仍待解決的問題

下一輪建議先寫新版本規格，**只移除purchase_month**，留下購買星期、小時與原核准等待。若之後獲准訓練，維持H60與全部角色名冊、未知政策、fit截止、train-only前處理、C=.1／1／10與原內層AP選參及完整評估；月one-hot移除後為7＋24＋1＝32維。暫不改等待轉換、門檻、類別權重、校準或加入其他特徵。

此假說要檢查「部分時間切分的月份類別缺乏成熟歷史支援時，模型是否過度依賴該欄」，不是宣稱月份已被證明有害。2月與4月外層月份已有歷史支援，低評率變化也不能由缺支援直接解釋；即使消融在三月較好，仍只是已看開發窗的敏感性結果。本輪沒有修改builder或開始消融訓練。

固定窗內回覆者的條件目標、未知標籤不可驗證、跨角色歷史重用及原事件入庫／版本缺口繼續存在。Stage 4的同ID全量核准清冊、雙時間版本與日結／入庫對帳仍待資料；本輪沒有新增正式提醒或Dashboard適用證明。
