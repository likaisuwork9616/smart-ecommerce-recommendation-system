# Stage 5：評論低評分預測可行性盤點

本文件保留前輪不限H的來源盤點與數字；最新已完成[訂單級資料集凍結](STAGE5_REVIEW_DATASET_SPEC.md)，固定60天窗口、逐角色as-of品質規則及內外層時間切分。下文72,613張不是新H60的合格標籤數；前輪整單品質隔離也不能直接用作歷史fit規則。兩輪均未訓練。

本輪評估現有Olist資料能否開始評論低評分的離線研究，只盤點問題定義、可用特徵與時間驗證。**沒有訓練、重新預測、選模、模型成績或Dashboard。** Stage 4維持[待資料與交接契約](STAGE4_OFFLINE_DAILY_ACCEPTANCE.md#data-handoff-kit)，原每日10%與五種子契約不變。

聚合證據與來源版本見[實際盤點](../reports/stage5/review_prediction_feasibility.json)。本文件是來源檢視後的研究建議，不是新增模型的事前訓練規格。可開始離線資料集與基線規格準備，但尚未證明核准時實際可得、全核准母體效能或可正式通知。

## 先固定要預測什麼

建議主問題為：**在訂單核准時點t，預測本單之後首份可辨識回覆是否為1–2分。** 1–2分為低評，3–5分為另一類；這是本輪提出的二元目標，不用評分平均、最低分或最後一份評論事後改標籤。

分析單位是一張訂單，不是一列評論、一個品項或付款紀錄。主分析先取購買與核准可解析、核准≥購買、核准早於2018-05-01的全部核准單，**不依最終已送達／取消或有無評論篩掉查詢分母**。此截止沿用既有Stage 4後段界線作本輪盤點範圍，並非依低評率或模型成績挑選；全評論表的鍵／時鐘檢查只是來源品質描述，不是保留測試效能。沒有核准時間的列無法指派t，另列缺口，不以購買日補值。

首答規則先以order_id在評論表建立唯一目標，再檢查相對於t的時序：

1. 核對評論身分、整數1–5分、建立／回答時鐘及矛盾紀錄，依最早記錄的`review_answer_timestamp`辨識首答。不能先刪掉t以前的回答，再改選一份較晚的評論。
2. 本輪採保守的整單品質隔離：同單任一評論缺鍵、(review_id,order_id)重複、分數／建立／回答時鐘無效或建立晚於回答，均不改挑別份評論。最早回答時間多筆平手時，即使同分也先隔離；不按ID任意挑。重複紀錄與後續評分變化分開對帳，評分後續不同本身不直接刪除首答。
3. 只有首答嚴格晚於核准t者才有本題的未來標籤；首答≤t另列異常。沒有評論、尚未回答或當下答案未可得者保留未知，不能當成3–5分或負例。
4. `review_answer_timestamp`僅暫作匯出快照的回答事件代理，不等於原系統取得時間；最早記錄也不證明原始首次評分版本。評論建立時間不用來提前宣稱答案已知。

主題是評分預測，不是以本單評論文字分類情緒。本單標題、文字、是否留文字及其他評論欄均不能作核准時輸入。

官方[Olist資料卡](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)記載，滿意度問卷可能在到貨或預估到貨日到期後發送；此處沿用前輪保存的官方資料卡內容。本次網頁讀取未取得可讀欄位字典，因此不額外宣稱`review_creation_date`等於實際邀評可得時間，亦不把回答時間稱為已驗證的原入庫時間。現有資料均沿原naive時鐘，業務時區／DST與評分修訂歷程仍未驗證。

## 預測時點比較

| 時點 | 可回答的問題 | 限制與本輪建議 |
| --- | --- | --- |
| 核准t | 下單／核准後、物流結果出現前的低評風險 | 作首輪主方案；仍需隔離已回答異常，輸入可得性只具快照假設 |
| 交運 | 已交運客群的後續低評 | 母體改成已交運單，缺交運入庫時鐘；不與核准主題混用 |
| 送達 | 已送達且尚未回答客群的低評 | 確有回答早於送達的紀錄；若先限送達又忽略既有答案，會改人群或洩漏，也失去未送達干預範圍 |
| 評論建立／問卷 | 接近問卷流程的回覆結果 | 欄位語義與實際可得時間未驗證；不能直接當作核准任務或答案成熟時間 |
| 回答之後 | 已有評分／文字的描述或分類 | 已經有本題答案；不屬於未來首答預測 |

本輪只建議核准主題，不同時開多個時點訓練，也不把較晚時點的物流資訊混入核准輸入。

在同一批72,613張主分析未來首答單中，4,122張首答早於送達、2,279張缺送達時點，其餘66,212張晚於送達；三者互斥，沒有同時刻。這是時點可行性對帳，不是送達特徵的模型增益或全母體比較。

## 候選特徵與洩漏邊界

可先參考[scripts/delay_features.py](../scripts/delay_features.py)的六表21欄基本聚合定義，**只借候選欄位與聚合方式，不呼叫其最終送達cohort／延遲label建構**。本輪未建Stage 5特徵快取，亦不載入Stage 4的101／102欄模型或分數。

| 群組 | 候選欄位 | 核准時可用性 |
| --- | --- | --- |
| 品項與金額（6） | item_count、seller_count、product_count、total_price、total_freight_value、freight_ratio | 明細先按訂單聚合；只有最終明細快照，核准前是否已齊、修改與取得時鐘仍為假設 |
| 付款（4） | payment_total、payment_count、payment_installments_max、payment_type | 付款獨立聚合後再join；追加付款／退款及取得時間未驗證，不能由最終總額反推當時已知 |
| 商品（3） | product_weight_g_mean、product_volume_cm3_mean、primary_category | 商品與主品項版本未驗證，缺值保留，不以全資料補齊 |
| 地區（3） | customer_state、primary_seller_state、interstate_item_ratio | 地址／主賣家快照有值不等於t時版本；缺州別不能當同州 |
| 時間與承諾（5） | estimated_delivery_days、approval_wait_hours、purchase_month、purchase_dayofweek、purchase_hour | 購買／核准時間可作事件代理；承諾修訂與取得時間未驗證，須另留不含承諾的敏感度設計，尚未執行 |

以上是**有條件的離線候選白名單**，不是21欄均已通過營運as-of驗收。items、payments先各自聚合至一張訂單一列，再以受控基數join；不能先把評論×品項×付款相乘而放大分母。ID只作連接、分組及追溯，不直接當模型輸入。

| 不採用項目 | 原因 |
| --- | --- |
| 本單review_score、文字／標題、建立／回答時間及評論存在與否 | 答案或答案流程資訊，通常在t後；不能當特徵或用來預篩查詢分母 |
| 本單實際交運／送達、實際耗時／延遲、最終status | 核准後結果或缺版本的最終狀態；不能把Stage 4分析出的實際延遲放入本題 |
| 本單之後才取得的明細／付款／承諾／主檔版本 | 在日結或事後才補齊不會使t時已知，不能靠重新命名欄位避開可得性問題 |
| 賣家／商品全期間低評率、全資料target encoding | 使用未來標籤；若日後研究歷史評論，僅可取他單在t前已發生且已可得的回答，另驗時鐘、排除本單並在訓練窗內處理 |

首輪不新增歷史評論特徵，先把唯一標籤、基本聚合及時間邊界做對。真實缺欄、孤兒join與一對多基數在盤點報告分開記錄，不能以最終快照完整率取代核准時可得率。

| 主分析的連接支援 | 實際結果 |
| --- | ---: |
| 核准單可連接客戶 | 73,254／73,254 |
| 至少一筆明細 | 72,676／73,254；578張缺明細 |
| 至少一筆付款 | 73,253／73,254；1張缺付款 |
| 明細列可連接商品／賣家 | 各83,009／83,009；這不代表商品屬性、版本或原取得時鐘齊備 |

缺明細或付款的訂單仍留在查詢名冊；未來若建特徵，需記缺值及處理規則，不能先刪掉使分母只剩完整案例。本輪只有鍵／欄位支援盤點，沒有計算這21個特徵值。

## 時間驗證建議與實際支援量

建議採月滾動的擴張歷史窗。以F表示每次月初fit截止，只能使用**核准t<F且首答在t之後、回答事件代理<F**的歷史標籤；等於F尚不使用。F是擬議訓練截止，不是原資料可得證明，也不與Stage 4日結交付時點T混用。

所有缺值補齊、編碼、標準化、校準、門檻及超參數選擇，只能在歷史訓練／內層時間驗證窗完成。內層也須重做自身fit時點的答案可得篩選，不能先用外層F已成熟的全部答案回填較早內層fit。同單全部評論只能落在同一order／query fold；回購顧客可跨時間出現，但需報customer_unique_id重疊，不當五份獨立資料。

下表以已檢視的2017-12、2018-02、2018-04日曆作**擬議開發窗口的資料支援盤點**；沒有模型fit或評分，也不是新的未知測試集。

| 擬議月初fit | 歷史有效核准單 | fit前已有未來首答 | fit當下尚未回答 | 匯出中無評論 | 早答隔離 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2017-12-01 | 39,463 | 34,254 | 4,871 | 329 | 9 |
| 2018-02-01 | 52,482 | 48,226 | 3,790 | 457 | 9 |
| 2018-04-01 | 66,476 | 61,827 | 4,064 | 576 | 9 |

評估候選須保留下一個完整核准月的全查詢名冊，再分答案已知、尚未知及異常；不得只留已評分訂單而隱藏回覆選擇偏誤。以固定的回答事件截止2018-05-01作本輪時鐘示例：

| 查詢月 | 全有效核准單 | 截止前可用首答 | 其餘未可用／異常 |
| --- | ---: | ---: | ---: |
| 2017-12 | 5,832 | 5,762 | 70＝較晚回答10＋無評論60 |
| 2018-02 | 6,706 | 6,623 | 83＝較晚回答27＋無評論56 |
| 2018-04 | 6,778 | 3,716 | 3,062＝較晚回答3,006＋無評論52＋早答4 |

四月若直接以這個截止只評已回答子集，會有明顯尚未可用的答案缺口。這只說明資料成熟度／回覆涵蓋，不表示四月模型較差。共用截止會造成不同月份的觀察長度不同，不能直接當公平效能比較。

正式訓練規格前，需先固定評估觀察截止／等長追蹤窗口、首答版本政策及已知／未知的計分規則。回答等待分位數、7／14／30／60／90天覆蓋只能作描述，不事後挑表現最好的等待天數；缺資料擷取與入庫完整性證據，也不能用最大回答日期宣稱所有答案已成熟。既有Stage 3與Stage 4已檢視Olist資料，後段月份不自動成為全新未知保留測試；日後另定保留方式並如實揭露先前檢視範圍。

未來若訓練，先報全名冊、已知／未知標籤與月份／回覆等待覆蓋，再在事先固定的已知標籤口徑報PR-AUC、召回、精確率及混淆表；必要時另看校準與介入成本。本輪沒有這些模型數字，標籤分布不代表可達效能。

## 本輪結論與下一步

| 面向 | 目前判定 |
| --- | --- |
| 可開始的工作 | 可準備核准時點、訂單級首答目標的離線資料集契約與最小基線規格；有現成多表及可辨識標籤，仍需先固定去重、缺漏與觀察窗口，沒有證明樣本足以達成效能要求 |
| 尚未通過 | 真實入庫／版本可得、未評論母體的代表性、統一觀察成熟度、保留測試設計、模型效能與正式通知適用 |
| Stage 4 | 維持待資料；不修改原四設定、每日10%、五種子及凍結結果 |
| Stage 5研究政策 | 本輪尚未設定訓練模型、種子、提醒預算或選參；Stage 4的10%不是抽樣只取10%訓練，五種子也不是五個fold |
| 未執行 | 訓練、模型重播／預測、效能計算、Dashboard與保留測試評分均0 |

下一步建議先凍結Stage 5訂單級資料集規格與標籤可得／觀察窗口，逐項驗證主鍵、首答規則、聚合基數及每個fit邊界；再另決定是否進入最小基線訓練。本輪不啟動該訓練。
