# Stage 4：固定模型，追查交運歷史稀疏、長承諾與 SP→RJ 的漏報

前輪[101／104 欄交運歷史比較](STAGE4_HANDOVER_HISTORY.md)發現，四月開發回測整體少抓三張延遲；主賣家歷史不足五筆、長承諾與 SP→RJ 的邊際結果也有退步。這三個視角可能重疊，不能直接相加，也不能先假定它們指向同一批訂單。

本輪固定已存在的 101／104 欄月份模型、核准時點、L2＝100、`topk10` 與每日 10% 預算，只讀前輪特徵及逐筆分數帳本。**不新增訓練、不重播模型、不選新模型，也不依四月分組設定混用規則。** 聚合結果保存於 [handover_sparse_diagnostics.json](../reports/stage4/handover_sparse_diagnostics.json)。

正式報告 SHA-256 為 `4aec5ec8c27c04ddfaac1d02ea39713ffd4d1288cbfc1baa5603ed58ef897c76`；來源綁定前輪 [handover_history.json](../reports/stage4/handover_history.json)、[handover_history_diagnostics.json](../reports/stage4/handover_history_diagnostics.json)、特徵及分數帳本，不生成新模型預測。

正式結果排除了原先的直覺：**四月的真正三重交集有 28 張訂單，卻沒有延遲，無法解釋退步。** 稀疏歷史的三張新增漏報，與歷史充足、長承諾 SP→RJ 的兩張新增漏報，是不同群組。四月整月仍是補抓 12 張、失去 15 張、淨少抓三張；本輪診斷沒有改變任何模型成績。

## 分組定義與檢查順序

| 維度 | 固定定義 | 解讀邊界 |
| --- | --- | --- |
| 交運歷史支援 | 0 筆／1–4 筆／至少 5 筆；另合併前兩組為不足五筆 | 不足五筆時兩個耗時分位缺失；事件數本身仍是模型輸入，不等於完全沒有新訊號 |
| 長承諾 | `estimated_delivery_days > 30`，含 30.x 天 | 使用核准時已存在的原承諾天數，不用實際送達耗時分組；「31+」沿用既有分箱名稱，不表示先把天數取整 |
| 路線 | 主賣家州 SP、顧客州 RJ | 訂單層級代表路線，不是包裹實際物流路徑 |
| 預測角色 | 九個歷史驗證 phase、三個開發回測 phase | 同一月份可在不同 fold 重複，歷史答案依當時截止點遮蔽 |

先各自檢查三個邊際，再看兩兩與三重交集，最後用 **3 種歷史支援 × 2 種承諾 × 2 種路線，共 12 個互斥格**驗證總和。另一個路線格包含所有非 SP→RJ 訂單及缺路線者；不把缺路線訂單默默刪除。邊際表描述重疊視角，不可加總為獨立損失；真正的三重交集才回答「稀疏歷史、長承諾及 SP→RJ 是否同時落在同一批訂單」。每組均保留樣本數、實際延遲、提醒、TP／FP／FN、補抓與新增漏報，避免只報淨額或只報補抓。

某組若沒有已知延遲，召回率為未定義，不記成 0% 或 100%；它只能說明該組在這份資料沒有延遲可供比較，不能證明模型已把這類風險處理好。少量延遲的單筆得失也不視為穩定趨勢。

報告沿用至少 30 張已知答案、至少 5 張延遲的群組支援旗標；不滿足任一條件即標示小樣本。四月與這些交集是從已看的結果提出的回溯描述目標，不是事前指定、尚未看答案的統計檢定。

## 每日排名與提醒名額如何核對

先在每個完整日，以原 101／104 分數各自遞減排序、訂單 ID 遞增處理同分，取 `floor(0.10 × N)` 個提醒，才切開上述分組。未知答案的訂單先參與全日競爭，再遮蔽答案；不把未知當準時，不替路線、支援或承諾子組另算 10%。每天各自取整，不跨日借額。

兩模型同一天提醒數相同，因此全日新增提醒與移除提醒數相同。逐筆新增漏報是「原 101 欄有提醒、104 欄不提醒，且已知實際延遲」；補抓則相反。完整日的取得與失去名額可以對帳，但沒有天然的一對一對手：不能將同日某張準時件直接宣稱為擠掉某張延遲件的原因，也不能把跨日期的得失互配。

排名位置一律使用原完整日排名。診斷會檢查漏報落在提醒邊界後方的哪一段，並比較同日哪些群組多取得或少取得提醒。各月份、路線與歷史支援的共現只提供下一次研究假設；104 欄重學了整棵樹與其他欄位分裂，觀察結果不能證明缺失補值或某個新增欄位造成個別錯誤。

## 下一次只做一個消融比較

建議下一次仍固定核准時點、L2＝100、`topk10` 與每日 10%，**只比較「事件數一欄的 102 欄」與「事件數加 p50／p90 的 104 欄」**，並保留原 101 欄研究對照。這能檢查兩個耗時分位在事件數之外是否提供穩定增益，先不一起加窗口、門檻或交互特徵。原前處理已包含缺失指示，不能將「再加一個是否缺失欄」當成本輪已證明的解法。

下一輪應在 fit 前固定全部月份、比較規則與分組，沿用歷史選模；同時報稀疏短承諾、歷史充足長承諾 SP→RJ 以及其他路線的得失，不能只針對四月損失調整模型或混用門檻。這只是根據開發診斷提出的研究假設，本輪未建立 102 欄資料、未訓練該模型，也不能預先宣稱會提高召回。

## 重現方式

沿用專案 `.venv/` 與前輪已生成的特徵、分數帳本及聚合報告，沒有新增套件或 MySQL 操作：

```powershell
.\.venv\Scripts\python.exe scripts\diagnose_handover_sparse.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

診斷讀取 Git 忽略的 `data/processed/olist_delay_handover_features.csv`、`data/processed/olist_delay_handover_scores.csv` 與前輪報告，並需要保留前輪使用的七份原始 CSV 及十九份模型檔供雜湊核對；訂單原始表也會用來核對答案時鐘。模型只查檔案雜湊，不反序列化或重播。GitHub 保存程式、方法、Notebook 及聚合報告；逐筆識別、原始資料、本機模型與執行狀態不提交。
