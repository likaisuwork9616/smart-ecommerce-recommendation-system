# Stage 12｜SQL 投票成本改善評估

**先拆量暫存表寫入、游標取列與 Python 精確加總，再擇一改動。** 原 48 筆每次有 136,381 列商品會員資料進入投票迴圈，整段耗時 1.485–1.613 秒。SQLite 已透過既有索引依工作階段取回商品，這次沒有理由新增同欄序索引。11 月 5 日僅審閱既有三次計時與查詢計畫，新增候選實作、排名及速度比較均為 0 次。

## 下一次怎麼量

現有計時從精確鄰居選擇結束後開始，到每個鄰居的會員筆數核對完成才結束。它包含公分母與權重準備、TEMP 表插入、SQLite 查詢與列轉換、逐列期限檢查、因果篩選、加總和完整性核對。1.485–1.613 秒是這些操作的合計。[計時邊界](../scripts/retailrocket_session_knn_sql_v4.py)

| 診斷分項 | 必須記錄 | 選擇候選的條件 |
| --- | --- | --- |
| 權重與 TEMP 插入 | 各自的秒數、選中列數、公分母位數、Fraction 分支次數 | 若 Python 逐筆送出 INSERT 占主要可改善時間，試 `executemany`，仍逐列檢查期限 |
| 查詢與取列 | execute 與各批 fetch 的合計秒數、批數、取回列數 | 若跨 Python／SQLite 邊界的費用突出，試固定批次 128 的 `fetchmany`。取列秒數包含 SQLite step 與 Python 物件轉換 |
| Python 投票與對帳 | 每批因果查詢／精確加總秒數、末尾對帳秒數、實際加總次數與每個 rank 的會員列數 | 若加總／計數占大頭，先檢查以連續 rank 對應陣列記數的可行性，保留逐 rank 應有筆數核對 |

診斷版以批次邊界計時，逐列保留原 `watch`、因果條件 `first < query_time` 與 SQLite progress handler。子項採互斥計時，附觀測器剩餘開銷，合計對回同一次外層投票計時。使用 `fetchmany` 診斷會改變取列方式，須先對回原輸出並量化觀測開銷。最後成對速度比較關閉額外分項計時，只以同樣的外層計時比較 A、B。

## 公平比較與採用條件

1. A 使用封存 V4 排名及 V6 保存。B 一次只試一項改動。先用合成資料驗證零鄰居、僅自己、未來商品與同時刻商品、499／500／501 邊界平手、超 64 位整數與切換 Fraction 的結果，並檢查查詢中斷及半筆寫入後的恢復。兩版都須保留完整鄰居池 SHA、原 tie 順序、500 邊界、精確權重、候選覆蓋與逐 rank 會員數。SQL 的 64 位 SUM 或浮點加總無法完整表達這套權重。
2. 鎖定同一台機器、封存 DB、來源、原 48 筆順序、Python／SQLite 版本與保存設定。每次開新 namespace。A、B 各暖機一次，再量六對，依序 AB、BA、AB、BA、AB、BA，保留每次值、執行順序及 cache 條件。每次四臂逐筆核對、ledger 的 **2,115,696 bytes** 與原 SHA 都須相同。任一不一致即停止候選。[原 48 筆參考與計時](../reports/stage12/retailrocket_session_knn_v6_refined_cost_20261103.json)
3. 主要比較每對 48 筆的核對、append 與完整 chunk 提交時間。用 verification 加「排除內含 commit 的 append」，再加所有 chunk commits 一次，保留直接 budget 保存。另列投票、rank、setup、尾端與完整入口，逐項標出內含關係。事前採用條件為六對中至少五對 B 的主要時間較短、AB 和 BA 各自的中位差都支持 B，且成對改善百分比的中位數至少 5%。這是工程決策門檻。保留全部六對與完整入口，若整段入口中位數反而變慢，先查原因，再決定採用。
4. 原 48 筆支持改善後，再用已驗的新 34 筆比較低鄰居帶，分別對回該組的參考 ledger。兩組各自報告配對差、最慢案例與細層缺口。當低鄰居帶結果尚缺時，改善結論僅限原固定 48 筆。

依 V6 每次 20.635–21.439 秒與初末來源核對 164.792 秒作規劃，14 次入口加一組初末核對約 **7.6–7.8 分鐘**。原 48 筆公平比較預留 **10–15 分鐘**執行時間，窗口上限 30 分鐘。這個預估從候選通過實作及合成驗收後起算，另計診斷與新 34 筆補測。這次評估尚無可報的加速比例，T_plan 待估，全量驗收關閉，預留測試鎖定。
