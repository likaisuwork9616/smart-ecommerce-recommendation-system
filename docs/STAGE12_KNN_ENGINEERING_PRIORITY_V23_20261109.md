# Stage 12：SQL 候選結案、來源驗證與保存成本

## 證據盤點

V17 `rank_counts` 投票候選與 V22 `group_before_size_join` 正重疊候選，兩者均沿用相同原 48 筆、順序、模型、子集與 binding，採用門檻也相同。這次核對 **637 份既有證據與方法、每次 63,941,600 bytes**，前後 SHA 均相符。

| 原始比較 | 來源 closure | 每次 closure 邏輯 bytes | checkpoint binding |
| --- | ---: | ---: | --- |
| V17 | 555 份 | 12,262,857,127 | 15 份、484,117,454 bytes |
| V22 | 580 份 | 12,265,783,628 | 同上 |

這些原始大型來源 bytes 來自封存 descriptor；本輪只重核報告、私人小型證據及方法，沒有重新讀取大型模型／原始資料。先前來源完整核對的事實沿用各輪收據。

V17 是原生 A、前後資源快照；V22 的 A／B 均有相同 SQL adapter，並有連續負載採樣。環境與原始 cohort 相同仍不代表當時機器狀態相同，候選結果只在各自窗口配對解讀，不跨輪混算速度。

接著從原始紀錄重算 28 次歷史 run、1,344 筆既有觀測，分清窗口、完整入口、主要成本與保存的巢狀範圍。尾端 commit 同時內含於 tail 及 primary，必須扣一次才能將入口拆成互斥成本。退出後的完整稽核沒有獨立總計時，不能用檔案時間或差值捏造成耗時。

盤點當時尚未排定優先順序；最終排序見下節。所有本輪新增 SQL 執行、樣本、訓練、完整 validation、主要 bootstrap 及保留測試均為 0。覆蓋仍 55／55 格、170 個可比較查詢、232 個歷史身分。

### 來源驗證路徑與尚缺的資料

依封存程式控制流程，每輪 worker 有兩次完整 request closure 核對；publisher 另有兩次完整核對。fresh run 的 `create` 與 writer 上鎖後會各核對一次 15 份 binding 來源，14 次 run 共 28 次；發布時開啟 14 份 store 又各核對一次。這是程式路徑推論，沒有新增 runtime 次數探針。每次 binding 邏輯覆蓋 484,117,454 bytes。

重複驗證分別保護建立時資料、上鎖後變更及獨立發布驗收；目前只可列為後續設計檢視點，不據此直接跳過、只比 mtime 或以舊快取代替。全 closure 與 binding 覆蓋有重疊，邏輯 bytes 不能當唯一資料量；也不能用固定 48 筆批次的比例推算完整 166,897-query validation 工時。

**未知項：**發布後處理沒有獨立 wall 總計時；每個 binding pass、context 載入、writer 取得、ledger proof 與輸出寫檔未各自拆時。完整 validation 的計畫工時仍未設定，不能捏造加速估計。

## 工程優先順序與下一輪交付

以下是依既有證據與正確性風險作出的工程判斷，**尚未實作優化、沒有新的加速比例**。目的先是釐清目前固定小批次工程流程的成本，不替完整 validation 預估工時。

### 下一輪先做第 1 項

固定同一批原 48 筆、順序、模型、binding 與原 V4／V6，先制定新觀測規格，再做合成驗收。應拆開：

1. 窗口前後 closure 雜湊與每次實際覆蓋的 descriptor／呼叫次數。
2. Checkpoint 建立、上鎖後 writer 再驗證、控制資料／context 載入與 catalog 準備。
3. 原 verifier、尾端、帳本 proof 與輸出保存；原主要成本定義保留。
4. 獨立 publisher 從開始到結束的 wall 總計時及內部分項，補齊目前未量到的部分。

驗收必須保留完整 payload／位元組、原呼叫次數及失敗順序，子段計時不超過父段；列明觀測器開銷。涵蓋同長度來源變更、前置驗證後至上鎖間變更、writer／恢復故障、發布時來源或帳本不符，均須拒絕。若實測仍沿用配對，順序、暖機、門檻與唯一窗口另行封存，不能把本輪成本判斷當作已批准的新候選成績。

這一項是補強觀測；不直接刪除重複驗證、不以 mtime／大小取代內容雜湊。原 API 的 SQLite `immutable` 使用方式也不構成所有來源不可被其他程式修改的證明。

### 第 2 項的前置條件

只有在分項證據確認成本後，才評估以完整來源 fingerprint、fit／設定版本為鍵複用不可變的 context／catalog，並保留逐 query 的因果時間篩選。來源、設定或 fit 改變後必須失效；空／未知／未來商品仍要維持完整原結果。

若要減少來源重驗，先證明快照或鎖定生命週期內原檔不能被寫入、替換或重新命名，並維持跨程序、上鎖及獨立發布邊界的保護。保留前後來源證據與故障測試，另立完整入口及主要成本的公平比較；本輪沒有聲稱這種設計已可用或能省多少時間。
