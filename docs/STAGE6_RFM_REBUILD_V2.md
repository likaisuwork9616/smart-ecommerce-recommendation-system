v2 是新的執行證據，沒有宣稱找回原私有檔或原測試收據。舊方法中的 v1 namespace 字串保留作為原方法 metadata；本輪實際資料、G1 描述、G2 分配與控制檔均在 `.runtime/stage6_rfm_rebuild_v2/`，以本輪規格的 `actual_private_namespace` 為準。

## 核對方式與完成條件

1. 準備時先核原 57 份來源，再實跑六套合成／回歸測試，凍結新入口、獨立參考程式、測試與實際 log。161 項通過，0 error／failure／skip，12.103883 秒；這是程式驗證，不是模型成績。
2. 建立新的顧客／逐單 RFM 資料集。獨立參考程式直接讀原始四表，另行判定事件資格、以 Decimal 加總金額並衍生顧客狀態，逐格比較完整 16＋16 欄，不呼叫原 builder、事件判定或顧客分流函式。
3. 私有資料包全部反讀後，才呼叫一次 G1 描述。與歷史聚合比較：非浮點欄位精確比型別和值；浮點欄位使用執行前固定的相對／絕對容差各 1e-12，另列實際差異，避免把不同平台的浮點尾差當成新結果。
4. G1 通過後呼叫一次原 G2 核心。每軸須有 2–5 個有效級數，每箱至少 `max(100, ceil(0.005 × n))` 人；相同數值不拆組，不為求通過改規則。原序、反序及 seed42 排列須完整同 ID 分配一致。
5. G2 writer 另從已核對的原 RFM 計算預期 rank、切點與每位顧客分配，反讀私有四檔，再發布公開聚合與外部 output guard。反讀不重新呼叫 G2 核心。
6. `--verify` 再核來源、原始四表與全部 RFM 值、G1 歷史聚合、G2 每 ID 分配及持久化 bytes；不重建資料集或重跑 G1／G2。

G2 不合格仍是完成的診斷結果，保留所有分配與失敗原因。技術失敗、部分輸出或缺 output guard 則不能宣稱完成；保留現場，不自動重播、刪檔或補造收據。

## 操作與保存

現有完成資料只使用只讀驗證：

```powershell
.\.venv\Scripts\python.exe scripts\rebuild_rfm_v2.py --verify
```

本輪依序執行過 `--prepare` 和 `--run`。兩者都是一次性操作，遇到既有版本或部分產物即停止；不要在目前工作目錄重新執行。單獨 Git clone 不包含私有資料與測試 log，須還原本輪備份才能驗證，不能靠刪除公開報告重新冒充同一輪執行。

不需真實資料的新增測試入口：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_rebuild_rfm_v2 -q
```

## 適用範圍與下一步

這是同一份 Olist 最終快照的描述性規則驗證，不是新時間資料、訓練、開發回測或最終保留測試成績。M 仍是商品毛額；原入庫、版本、退款與結算資料仍不足。G2 通過也不等於真實客群、未來價值、回購或行銷成效已獲驗證。

本輪止於 G2。建議下一步依原事前規格執行 G3：五種子 80% 顧客抽樣估切點、回套同一完整參考名冊，逐種子檢查級數、每箱支援、每軸 agreement≥0.90 及 joint ARI≥0.80；不因小組不足而臨時改切點或門檻。G3 尚未執行，也不命名商業客群。Stage 4、5 維持待資料，延遲提醒預算維持每日 10%，Dashboard 繼續暫緩。
