## 同一查詢的波動分解

下表每格選「核心成本重測變幅最大」的同一筆查詢，從最快觀測到最慢觀測比較。Δ核心＝同一對觀測的 Δverify＋Δappend（扣 commit 與直接預算寫入）；投票 SQL 與精確加總已包含於 verify。單位毫秒，四捨五入後可能有尾數差異。不同分量的各自最大值不拿來相加。

| 細層 | 原組／最快→最慢次序 | Δ核心 | Δverify | Δappend | 內含 Δ投票與加總 |
| --- | --- | ---: | ---: | ---: | ---: |
| `0100/n3/v4` | V6／1→3 | +194.947 | +193.604 | +1.344 | +154.198 |
| `0001/n3/v3` | V16／1→2 | +108.221 | +15.915 | +92.306 | +12.484 |
| `1101/n6/v5` | V6／3→2 | +84.932 | +38.879 | +46.053 | +9.215 |
| `1001/n4/v4` | V6／1→3 | +82.439 | +83.942 | -1.504 | +78.449 |
| `1101/n4/v4` | V6／3→1 | +77.421 | +32.427 | +44.994 | +21.910 |

`0100/n3/v4` 的主要變幅落在驗證，且其中投票與精確加總占較大部分；`0001/n3/v3` 則以 append 波動為主。`1001/n4/v4` 的該對觀測，扣除直接預算寫入後的 append 反而略降，不能把未扣預算的數字當成核心變慢原因。這些定位到計時區段，仍不足以辨認 OS 排程、磁碟、快取或特定背景程序的因果影響。

中位數平均情境的前三格貢獻合計約 **50.1%**；其中 `1101/n5/v4` 只有一個不同查詢。四個單樣本格母體合計 **11,415 筆**，重測三次仍無法估計格內不同查詢的差異。後續成本規劃須保留這個限制。

投票 SQL 與精確加總仍是值得評估的部分，但目前 55 格紀錄沒有把取列、Counter 計數與精確加總逐一拆開。後續候選選擇會同時參考既有原 48 筆細項診斷與已失敗的批次取列結果，並用原固定樣本的新配對測量決定是否支持候選。

## SQL 投票路徑候選與事前門檻

以目前封存 SQLite 3.49.1 模型重新執行唯讀 `EXPLAIN QUERY PLAN`，主資料庫前後 SHA-256 一致。計畫掃描小型 chosen 表，再透過 `sqlite_autoindex_m_1` covering index 依 `(v,s)` 查會員資料；索引已含商品欄位。這一步沒有執行推薦查詢。另以人工整數案例核對 SQLite `SUM` 的 64 位溢位，保留原 Python 大整數／Fraction 精確加總。

| 候選 | 本輪判斷 |
| --- | --- |
| 新增同欄位會員索引 | 已有 covering index，缺乏新增依據 |
| SQL SUM／浮點聚合 | 64 位溢位或失去精確性，不能替代既有權重 |
| fetchmany(128) | 保留前輪失敗結果：六對僅兩勝、中位改善 −0.36%；本輪不重調批次大小 |
| executemany 插入 | 舊兩次細項診斷合計約 0.187 秒；本輪未選 |
| rank_counts | 本輪選定；只將 Counter 改成按連續 rank 索引的 list，待公平比較 |

原 48 筆兩次細項診斷中，accumulate＋check 合計 **0.437784 秒**，是未被前輪配對否決的候選中較大的歸屬區段。但改用陣列只影響其中計數容器操作；逐列 watch、因果商品查找、精確加總、會員筆數驗證仍執行。此數值還來自開啟細計時且使用批次取列的診斷路徑，不能當成 baseline 可省時間。

候選沿用既有、經合成驗證的 V7 `rank_counts` 模式，SQL 查詢與讀取列數不變。原 V4 基準、完整鄰居池 SHA、精確相似度、同分順序、第 500 位切點、逐鄰居會員數及四臂輸出均保留。沒有新增正式模型或更換樣本。

先固定原 **48 筆**、相同順序與來源。A 原版、B 候選各暖機一次，再做六對 **AB、BA、AB、BA、AB、BA**，每次使用新唯讀連線與 checkpoint。主要比較時間為 **verification＋append 扣內含 commit＋所有 chunk commit 一次**，保留直接預算保存；此口徑與前述排除直接 budget 的細層核心成本分開。另列投票、rank、setup、尾端與完整入口，暖機不納入六對。

採用條件全部事前固定：**至少五對候選較快、AB 與 BA 各自的節省中位數皆為正、成對改善中位數至少 5%，且完整入口中位數不得變慢**。每次須對回原 48 筆的 **2,115,696 bytes** 與同一 payload SHA。只有原 48 全部通過，才對既有固定 34 筆低鄰居樣本執行同規格比較；否則結束本候選，不追加對次或改挑其他候選。

每組共用原 1,800 秒絕對期限與既有記憶體／磁碟限制。任一來源、規格、方法、輸出、計時、期限或退出檢查失敗即停止發布。初末與退出後核對來源、保存內容及原期限；比較 34 的入口還須從保存的 48 筆計時重建通過結論。

機器背景負載可能變動，OS 檔案快取也會受來源驗證與前序執行影響。每次入口外另存非阻塞系統 CPU／記憶體觀測；CPU 值描述兩次觀測間的平均背景，第一筆受初始化時點影響。它不計入主要計時，也不能單憑快照歸因於某個程序或推算 Ollama 減速百分比。重實測循序執行，其他服務維持原設定。[封存候選與完整規格](../reports/stage12/retailrocket_session_knn_v17_cost_sql_specification_20261106.json)
