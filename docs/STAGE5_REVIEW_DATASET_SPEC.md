# Stage 5：訂單級首答資料集凍結規格

後續已完成[最小基線與評估規格](STAGE5_REVIEW_BASELINE_SPEC.md)，沿用本版H60標籤、角色與截止；只新增契約稽核，沒有重標、訓練或改寫本版程式／報告。以下保留資料集凍結當輪的數字與驗證紀錄。

本輪承接[可行性盤點](STAGE5_REVIEW_PREDICTION_FEASIBILITY.md)，固定核准時預測首答1–2分的訂單級資料集及時間切分。**只建標籤／切分中繼資料與核對證據，不建21欄特徵值、不訓練、不預測、不算模型效能、不做Dashboard。** Stage 4維持待資料與原每日10%／五種子設定。

以下H、截止與內外層規則先固定，再執行本輪窗口支援量對帳；未比較不同H或模型成績來選規格。正式機器可讀[資料集規格](../reports/stage5/review_dataset_specification.json)綁定來源、規則與程式版本，[實際核對](../reports/stage5/review_dataset_audit.json)只報聚合資料支援。這是已檢視快照上的研究資料契約，不是尚未決定的模型訓練／選參事前規格，也不是營運可得性驗收。

## 固定研究問題與母體

| 項目 | 凍結規則 |
| --- | --- |
| 單位與查詢 | 一張訂單一列，t＝order_approved_at；ID只供連接、分組與追溯，不當特徵 |
| 主分析母體 | 購買與核准可解析、核准≥購買、核准<2018-05-01；沿前輪73,254張完整研究查詢名冊，不篩最終送達／取消、有無評論或缺特徵 |
| 首答目標 | 最早記錄回答在`(t,t+H]`內時，1–2分為y=1、3–5分為y=0；後續評分不同不改用最差／平均／最後分數 |
| H | 固定60個elapsed days，使用Timedelta而非兩個日曆月；窗口左開右閉，回答恰在t+H可納入 |
| 全域觀察截止C | 2018-07-01 00:00 exclusive；用於全域中繼資料與外層查詢標籤，不把它當原擷取／入庫完成證據 |
| 完整觀察窗 | 在角色答案截止A，須`t+H<A`；等於A仍未成熟，不以「已早答」跳過成熟閘 |
| 未知 | 無可見回答、首答超H、未成熟或品質隔離均保持nullable y，不能補成0／高分；不是「60天內未低評就算負例」 |
| 可解讀範圍 | 固定窗內回覆者的首答評分條件目標；未知者仍留在名冊及涵蓋對帳，不能外推所有未評論者的低評風險 |

H=60是本輪統一追蹤機會的設計選擇，未宣稱最佳業務等待期或全部答案已收齊。C選在既定核准月份的H窗之後；仍逐列檢查`t+H<C`，不用最大回答日期推定成熟。來源時間沿原naive字串，沒有擅自指定UTC、業務時區或DST。

## 多評論與每個截止的可見資料

前輪可行性盤點曾對同單任一壞評論做整單隔離；那是固定快照品質描述，**不能直接沿用成每個歷史fit的標籤**。本輪按角色截止A重建：

1. 回答時間可解析的列，先限`answer<A`。發生於A或之後的評論不能參與首答選擇、品質隔離或未知原因；不可因一筆未來壞評論，回頭刪掉較早fit的可用標籤。
2. 先辨識可見的最早回答，保留answer≤t的列；首答≤t就隔離，不先刪早答再改挑後答。可見首答>t+H為超窗未知，沒有可見回答則統一記截止時無可見答案，不根據全快照透露日後會不會回答。
3. 窗口品質檢查只用同單可見且answer≤t+H的列。缺review key、重複(review_id,order_id)、非整數1–5分、缺／無效建立時間或建立晚於回答，列品質隔離。H後的壞評論不回頭污染固定H目標。
4. 最早可見回答在H窗內且有多筆平手時，即使同分也隔離，不以ID任意挑；H後的平手仍屬超窗未知。review_id跨訂單重用不當全域重複；後續不同分數本身不造成首答歧義。
5. 回答時間缺失／無法解析的來源列無法放入歷史前後，另列靜態來源品質缺口並隔離所屬訂單；不能假裝知道它在A之前或之後。缺order_id或無法連接的來源列需另列來源問題，不默默丟棄。

所有判定仍是**回答事件時間代理回放**。目前缺原入庫與評分修訂歷程，不能證明某分數版本在歷史fit真實已可查詢；帶舊事件時間的事後更正也無法由本快照識別。C時點的標籤不可直接當作較早fit標籤，必須使用各角色自己的截止重建結果。

## 內外層日曆切分

外層沿用已檢視的三個開發核准月；沒有重新宣稱未知保留測試。F為外層fit截止，I為內層fit截止，C為全域事件觀察截止。

內層查詢月由純日曆規則決定：**取滿足`month_end+H≤F`的最近完整核准月**，其月初為I。由於t<month_end，這保證整個內層查詢月在F時`t+H<F`；不用固定減幾個月去近似60天。

| 外層fit F | 外層查詢區間 | 內層fit I／內層查詢區間 | 內層驗證答案截止 | 外層查詢答案截止 |
| --- | --- | --- | --- | --- |
| 2017-12-01 | [2017-12-01,2018-01-01) | I=2017-09-01；[2017-09-01,2017-10-01) | F=2017-12-01 | C=2018-07-01 |
| 2018-02-01 | [2018-02-01,2018-03-01) | I=2017-11-01；[2017-11-01,2017-12-01) | F=2018-02-01 | C=2018-07-01 |
| 2018-04-01 | [2018-04-01,2018-05-01) | I=2017-12-01；[2017-12-01,2018-01-01) | F=2018-04-01 | C=2018-07-01 |

| 角色 | 候選名冊 | 標籤截止A與用途 |
| --- | --- | --- |
| inner_train_pool | t<I的全部主分析訂單 | A=I；只讓成熟且有合法窗內首答者提供訓練候選y |
| inner_validation | 內層完整核准月 | A=F；保留全查詢名冊，成熟且合法者才有驗證標籤，不回填內層訓練 |
| outer_train_pool | t<F的全部主分析訂單 | A=F；選參後擬議重訓的歷史候選，仍須重新套用F閘 |
| outer_evaluation | 外層完整核准月 | A=C；保留全查詢名冊，未知／隔離另報，不用測試答案選參 |

兩種訓練池都要求`t+H<A`、首答在`(t,t+H]`且answer<A。已回答但H未滿者可報為「可見早答、未成熟」，y仍為NA，不提前收入最近訂單以免偏收快速回覆者。這是候選標籤閘，沒有執行任何模型fit。

每個外層fold內，inner_train與inner_validation訂單不重疊、outer_train與outer_evaluation不重疊，outer_evaluation也不進內層。內層驗證月成熟後可進outer_train，是正常的選參後歷史重訓候選；inner_train與outer_train重疊及不同滾動fold重用過去訂單均需揭露，不能當作獨立樣本或五份資料。

未來若訓練，缺值補齊、編碼、標準化與估計器擬合只用該次fit合格訓練列；選參使用歷史內層驗證，若需要校準或門檻選擇，須另定內層／歷史out-of-fold規則，外層查詢答案一律不能參與。內層以I截止重建，不能用F或C的未來答案回填；確定設定後才可用F合格歷史做外層重訓。21個基本候選欄位的快照可得性假設沿[前輪白名單](STAGE5_REVIEW_PREDICTION_FEASIBILITY.md#候選特徵與洩漏邊界)，本輪不生成X，也不借Stage 4的延遲label或凍結分數。

| 產物 | 契約 |
| --- | --- |
| 公開規格 | 凍結H、C、母體、首答政策、日曆切分、來源及程式SHA；規則或來源變更需另版本，不覆寫不同內容 |

| 私有split_membership.csv | 每fold／角色保留全部候選ID、角色截止、成熟與標籤狀態；僅角色合格標籤可填y，不另附可洩漏的完整未來答案欄 |
| 私有manifest.json | 綁規格、來源與私有檔bytes／hash及列數；只留Git忽略路徑，不將私有digest放公開報告 |

私有產物預定放`.runtime/stage5_review_dataset_v1/`，只是標籤／切分中繼資料，不是特徵快取、模型或通知名單。先檢查整個bundle，既存任一內容不同即拒覆寫；寫出後反讀schema、nullable y、時間、ID、角色順序與逐值一致性。公開只交付聚合，不提交原始評論、文字、ID／ID hash或逐筆標籤。

私有欄位白名單如下；這些全是身分、標籤與審計中繼資料，不能直接當X輸入。

| 檔案 | 固定欄位 |
| --- | --- |
| order_labels.csv（9欄） | order_id、prediction_time、window_deadline、observation_cutoff、horizon_complete、label_state、role_label_usable、y、first_visible_answer_at |
| split_membership.csv（12欄） | outer_fold、role、fit_at，加上述9欄 |

`first_visible_answer_at`只可填A之前已可見的事件代理，不附日後首答時間。未知／不合格列的y必為空，也不另附review_score或能繞過成熟閘的低／高分欄；label_state只有合格列可區分已知低評／其他分數。C全域標籤檔只作C狀態審計，歷史fit必須使用角色檔的遮罩後y，不能從C檔再join回完整未來答案。

每個角色須對帳完整候選數與互斥標籤狀態，另外報已早答但未成熟的排除量。可用列的`answer>=A`或`t+H>=A`、同fold訓練／查詢重疊、未知y被填成0等違規須為0；任何未通過都停止交付，不能靠刪掉未知列或缺明細／付款的列縮小分母通過。

本輪能核對事件代理的fit資格，**不能核准真實歷史取得時間**。來源觀測／入庫、評分版本與線上特徵可得仍列未驗證；沒有新資料就保留此限制，不因此重新訓練或製作Dashboard。

## 重現與交付判定

備妥原九CSV及專案`.venv`後，在專案根目錄執行：

```powershell
.\.venv\Scripts\python.exe scripts\freeze_review_dataset.py --specification-only
.\.venv\Scripts\python.exe scripts\freeze_review_dataset.py
.\.venv\Scripts\python.exe -m unittest tests.test_review_dataset_contract -q
```

先以既有可行性報告的固定SHA驗來源、九表header與先前分母，再把H／C／政策／日曆及14份來源／程式綁入正式規格；稽核只讀orders四欄、reviews五欄、customers兩欄，不讀評論文字或生成特徵。JSON以嚴格鍵／finite值解析；來源、規格或既有輸出不同即拒收，改設計需另版。所有輸出解析後須在專案內，私有bundle還須在Git忽略的.runtime。
