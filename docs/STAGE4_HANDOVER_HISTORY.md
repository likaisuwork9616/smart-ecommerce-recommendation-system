# Stage 4：核准時點新增主賣家交運歷史，101 欄對照 104 欄

前輪[物流訊號與預測時點盤點](STAGE4_LOGISTICS_AVAILABILITY.md)確認，原 101 欄尚未使用過去訂單的核准至交運耗時。本輪保留核准時點、L2＝100、`topk10`、原評分群體及每日 10% 提醒預算，只新增主賣家的三個交運歷史欄位，檢查是否減少漏報，以及改善是否要以其他月份或路線退步交換。

本輪八次新訓練完成。104 欄在七月、九月歷史驗證及十二月開發回測分別多抓 1、3、1 張延遲，兼顧這三個已知描述性目標；但八月少抓 1 張、四月開發少抓 3 張，固定候選三個開發月合計反而 TP 339 → 337、召回 20.65% → 20.52%。完整歷史選模未採用新候選，研究主方案仍 TP 413、召回 25.15%，沒有將局部改善當成全面進步。

方法見[訓練前規格](../reports/stage4/handover_history_specification.json)，SHA-256 為 `9171fc9648991243a78046cf8620fe3f5feadf59bfc37b1a2eae9e646f8cf8cc`；數字來自[實驗報告](../reports/stage4/handover_history.json)與[診斷報告](../reports/stage4/handover_history_diagnostics.json)。來源綁定前輪完整 76 候選報告及原特徵快取的雜湊，不按本輪開發結果追加參數或特徵搜尋。

## 唯一改動：三個數值欄位

| 項目 | 既有研究對照 | 新候選 |
| --- | --- | --- |
| 候選 | `xgboost_rank_backlog_7_14d_l2_100_topk_10` | `xgboost_rank_handover_104_l2_100_topk_10` |
| 輸入白名單 | 101 欄：93 個數值、8 個類別 | 104 欄：96 個數值、同 8 個類別 |
| 新增輸入 | 無 | 主賣家 90 天交運事件數、核准至交運耗時 p50／p90 |
| L2／訓練配對 | 100／`topk`、整數 10 | 全部相同 |
| 模型操作 | 重播既有八個月份版本 | 相同月份、成熟訓練訂單與日群組，各 fit 一個新版本 |

三個新欄位為：

| 欄名 | 定義 |
| --- | --- |
| `seller_handover_count_90d` | 同主賣家、有效交運事件落在 `[t−90天, t)` 的其他訂單數 |
| `seller_handover_p50_hours_90d` | 上述事件的「核准 → 交運」小時數中位數；至少 5 筆才計算 |
| `seller_handover_p90_hours_90d` | 同組小時數的第 90 百分位；至少 5 筆才計算 |

t 是每張訂單自己的核准時間。窗口依**交運事件時間**決定，包含恰好 t−90 天，排除恰好 t 與所有未來事件；不按交運所屬訂單的核准月份或最終送達日決定窗口。分位數固定用 NumPy `linear` 插值，不搜尋其他窗口、支援門檻或分位數。耗時保留小數小時，合法的 0 小時可保留，負值不修成 0。

主賣家沿用既有規則：單筆品項價格最高者，同價取較小的 `order_item_id`。每張訂單只產生一個交運代理事件，多品項不重複計數。缺主賣家時事件數為 0，p50／p90 缺失；不把不明賣家合併成人造群組。事件數少於 5 時保留實際筆數，兩個耗時欄留缺失，補值器只用成熟訓練資料擬合。每筆查詢均排除自己的訂單 ID，即使外部輸入的時鐘有錯也不能讀到自己。

## 避免在核准時讀到未來

歷史事件要求 `購買 ≤ 核准 ≤ 交運`，不讀最終 `order_status`，不要求最終已送達，也不使用標籤、承諾日或評論判斷是否加入。缺送達時間仍可貢獻合法交運事件。

另隔離「送達早於交運」的矛盾。這不使用未來送達提前刪除歷史事件：可進入某查詢窗口的交運必須 `< t`，若送達 `< 交運`，則該送達也必然 `< t`，矛盾在當下已經可見。送達晚於交運或仍缺失的事件，不會因最終送達耗時與延遲結果而被排掉。

新增特徵只為核准嚴格早於 **2018-05-01** 的原建模查詢點建立；原始交運與送達歷史也在此邊界遮蔽。原快取的欄位、值、索引順序與評分母體保留，沒有替原保留期間建立新特徵或評分。模型標籤母體仍是時間合理且最終已送達的訂單，不能因此宣稱已驗證取消或始終未送達訂單的延遲預測。

這三欄是「與代表主賣家關聯訂單的交運紀錄」，不是逐包裹、逐賣家實際備貨速度。Olist 沒有逐品項交運、取消時間、事件入庫延遲或主檔版本紀錄。事件時間代表及時可用資訊仍是研究假設，歷史已交運群體也會漏掉尚未交運的慢件；本輪沒有同時加入未交運負載。

## 訓練、提醒與歷史選模維持

所有使用者設定的分類器參數與原 101 欄一致：400 棵樹、學習率 0.05、深度 4、`min_child_weight=10`、行／欄取樣 0.8、`hist`、seed 42、fit 兩執行緒、評分一執行緒。目標仍為 `rank:ndcg`、二元 gain、`ndcg_exp_gain=False`。`eval_metric=ndcg@20` 不變，沒有 `eval_set`、early stopping、外部權重或續訓。

只有數值前處理白名單多三欄；補值與類別編碼規則維持，樹模型不新增數值標準化，統計仍只在訓練列 fit。欄位取樣比例雖相同，輸入多三欄後模型的特徵維度、實際取樣結果、樹、截距與訓練期末亂數狀態可以改變，不能宣稱保存後的模型狀態完全相同。

訓練答案沿用 `deadline_wait0`：核准時間與 `min(實際送達時間, 原承諾日次日午夜)` 都嚴格早於模型月初。按核准時間、訂單 ID 遞增穩定排序，以成熟訓練列的核准日組 query；全準時或全延遲的日群組不刪除。`topk10` 仍是訓練的固定配對焦點，不是對每天訂單量自動取 10%。

分數仍為嚴格單調的 `sigmoid(raw margin)`，用來接上既有分數介面，沒有校準成延遲機率。每日完整、已結束批次先以分數遞減、ID 遞增排序，取 `floor(0.10×N)` 個提醒；每天各自取整，不跨日借額。完整批次含當時答案未知的訂單，先排名再遮蔽未知答案，不能縮小分母或將未知單當準時。特徵在核准時凍結，但日結提醒可能比核准晚最多一天。

| 開發月 E | 歷史驗證月份 | 歷史答案截止 |
| --- | --- | --- |
| 2017-12 | 2017-07、08、09 | 實際送達 `< 2017-12-01` |
| 2018-02 | 2017-09、10、11 | 實際送達 `< 2018-02-01` |
| 2018-04 | 2017-10、11、12 | 實際送達 `< 2018-04-01` |

八個月份版本為 2017-07、08、09、10、11、12、2018-02、04；各歷史月由當月版本預測，不拿較晚模型回頭評訓練資料。本輪八次新 fit、八份既有 101 欄版本重播，舊 76 個候選指標逐值凍結，再加一個新候選，共 77 個。其餘 600 份舊月份版本未重新評分。

主方案保留原規則：先最大化三個歷史月的最低召回，再比較歷史合計 TP、原始 AP、固定候選順序。每月 30% 是適用要求，不是先刪除未達標者再另選模型。另列原 76 候選組與 101／104 兩候選組，清楚區分固定模型比較、兩候選歷史選模、完整主方案，不能把開發最高分候選直接當成主方案。

七月、九月的描述性對照分別是 2017-12 fold 已知歷史 TP 21、52；十二月開發 TP 65。這些已知目標不參與選模。十二月在 2018-04 fold 是另一組成熟歷史答案，不能與十二月開發完整答案混用。

### 月份改善仍包含局部退步

| 期間與觀察 | 實際變化 | 解讀 |
| --- | --- | --- |
| 七月歷史 SP→SP | TP 13 → 11；提醒 290 → 288 | 整月多抓 1 張，這條路線仍少抓 2 張 |
| 九月歷史 SP→RJ | TP 8 → 11；提醒 67 → 81；FP 59 → 70 | 多抓 3 張，代價是該路線多 11 張誤報 |
| 九月歷史 SP→SP | TP 9 → 10；提醒 112 → 104；FP 103 → 94 | 該路線提醒更少，卻多抓 1 張並少 9 張誤報 |
| 八月歷史 SP→SP | TP 7 → 5 | 是第一個 fold 歷史下限退步的其中一處 |
| 二月開發 | 補抓 43 張、失去 43 張 | 總數持平，提醒對象並未相同；SP→RJ、SP→SP 各少抓 4 張 |
| 四月開發 SP→RJ | TP 23 → 20；提醒 263 → 248 | 這條路線少抓 3 張，但其他路線同時也有得失 |
| 四月開發承諾 31+ 天 | TP 7 → 3；提醒 56 → 42 | 長承諾組少抓 4 張，值得與歷史支援量交叉檢查 |

路線與承諾是重疊視角，不能把四月的 −3 和 −4 相加當成少抓 7 張。小路線或少數延遲的變動也不足以證明穩定趨勢；診斷提供樣本數與支援旗標，不因一筆得失作因果解釋。

十二月每日量也不一致：1–99、100–199、200–399 三組 TP 各少 1 張，唯一 400+ 訂單日由 3 → 7，才使整月淨額為 +1。該日只有一個完整批次、415 張訂單，不能據此宣稱大批次穩定受益。

建議下一步先固定現有模型，交叉檢查**少於五筆歷史、四月長承諾及 SP→RJ**的漏報與完整日名額交換，再查看同類情況在較早歷史月是否重現。先分清楚是歷史支援稀疏、路線分布還是排名邊界交換，才提出下一個小改動；本輪不立即擴大特徵、窗口或參數搜尋，也不事後用已看的四月分組訂模型混用規則。

## 重現方式

沿用 `.venv/`，沒有新增套件或 MySQL 操作。先完成前輪資料快取及本機模型，再執行：

```powershell
.\.venv\Scripts\python.exe scripts\train_handover_history.py --specification-only
.\.venv\Scripts\python.exe scripts\train_handover_history.py --n-jobs 2
.\.venv\Scripts\python.exe scripts\diagnose_handover_history.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

訓練前規格為 [handover_history_specification.json](../reports/stage4/handover_history_specification.json)。執行前固定來源、白名單、事件窗、支援門檻及選模；`--reuse-new-versions` 只允許重播本輪規格與來源均一致的新版本，不能跳過溯源檢查。診斷只讀已存在分數，不 fit、不重播模型、不改選。

新快取保存在 Git 忽略的 `data/processed/olist_delay_handover_features.csv`，分數為 `data/processed/olist_delay_handover_scores.csv`。八份新版本在 `models/research/handover_history_versions/`，各開發月主方案 artifact 為 `models/research/olist_delay_handover_YYYY-MM.joblib`；GitHub 只保存聚合報告，不上傳原始資料、私人訂單識別、模型或本機執行狀態。
