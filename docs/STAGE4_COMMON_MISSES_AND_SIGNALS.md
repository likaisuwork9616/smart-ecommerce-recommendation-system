# Stage 4：固定三模型，分析共同漏報、排名交換與核准可用訊號

前輪[101／102／104欄消融](STAGE4_HANDOVER_COUNT_ABLATION.md)發現，只加交運事件數會補回部分指定漏報，也會失去其他延遲訂單。本輪保持三個排序研究對照、核准時點、L2＝100、topk10與每日完整日10%預算，先分清楚共同弱點與提醒對象交換，再盤點下一次可測的訊號。

本輪沒有訓練、載入或重播模型，沒有校準、調門檻、改選或混用模型，也不重新評估原保留測試。研究主方案仍維持三個開發月TP413、召回25.15%、歷史下限19.63%；該主方案包含既有Logistic，與本輪三個固定排序對照不同。

## 資料角色與完整日預算

來源為[凍結訓練報告](../reports/stage4/handover_count.json)、[既有路線診斷](../reports/stage4/handover_count_diagnostics.json)，以及Git忽略的137欄特徵快取與192,168列三模型分數帳本。八個月份模型各自對當月評分；同一歷史月份在不同fold出現時，保留各自的實際送達答案截止，不能當成獨立樣本加總。

三個候選分別為原101欄、原101加交運事件數的102欄，以及再含核准至交運耗時p50／p90的104欄。每張訂單在自己的核准時間凍結特徵；提醒於完整已結束日曆日排序後分配，可能比核准晚最多一天。

先將每個完整日所有訂單按分數遞減、ID遞增排序，各模型取`floor(0.10×N)`個提醒，才套用歷史答案已知遮罩。未知答案仍參與名額競爭，不當準時，不按路線或支援組另給10%。歷史驗證答案要求實際送達嚴格早於fold月初；十二月、二月、四月為已反覆檢視的開發回測。

## 三模型共同漏報的定義

捕捉組合固定按101／102／104順序記錄八種互斥模式。對已知延遲而言，`000`是三者都未提醒、`111`是三者都提醒，其餘六種表示模型間有差異。完整報告同時保留準時與未知答案的模式，不能把`000`內所有訂單都稱作延遲。

共同漏報按所有實際路線、既有五個承諾分箱、交運歷史0／1–4／至少5筆、完整日量分箱拆解。各維度都是描述視角，彼此重疊；同一個維度內才可對帳加總。零延遲群組的比率留空，不填成0%或100%。

完整日排名、排名百分比及「排名−當日容量」用來描述離提醒邊界有多遠。三者中最接近的排名，只是回溯描述，不是已訓練的選模器；將三模型抓到的訂單取聯集，也沒有維持每日10%容量，不能把聯集當新模型的召回率。

排名交換以101→102、101→104、104→102三組對照分開記錄補抓、新增漏報、誤報及每日路線名額。總量流出／流入是計數記帳，不代表某張準時單直接擠掉指定延遲件，也不證明某欄位造成錯誤。

## 核准時點訊號的盤點方式

已有101欄包含靜態訂單、路線與送達歷史、未送達待件、地理交互，以及7／14天逾期待件變化。102／104欄又已測過過去交運事件摘要，因此不能把這些重新列為尚未測試的方向。品項`shipping_limit_date`已做過八欄敏感度分支，且缺建立與修改版本，不當作已確認的新訊號。

本輪額外盤點「主賣家已核准、但截至查詢尚未觀測交運或送達」的歷史訂單。它與既有「尚未送達」待件不同：已有交運而仍在運輸中的訂單，不屬這個新代理群體。這是核准當下可回溯的候選訊號，不是本輪模型輸入或新預測成績。

只檢查兩個候選：近90天此類歷史訂單的件數，以及仍等待的核准時齡p90。每筆查詢只用`[t−90天,t)`的較早核准，排除本單；實際交運及送達事件必須嚴格早於t才算已觀測。等於t仍未知；已觀測的矛盾時序需隔離，不能用未來送達或最終狀態提前刪除。

事件未觀測不代表貨物實際仍在賣家手上。缺取消時間、入庫延遲與主檔版本，仍可能含取消或延遲登錄的歷史訂單。原始資料也沒有承運商、物流掃描、庫存、人力、即時天氣或交通；不能從現有CSV補出這些資訊。

兩個訊號使用固定分箱比較共同漏報、其他已知延遲、準時及未知答案的覆蓋與分布，不找最佳切點。分布差只能支持研究假設，不能證明加入特徵後會提高召回；下一次訓練仍需相同資料時點、完整日容量與歷史選模對照。

## 本輪實際結果與驗證

### 共同漏報多於三者分歧的延遲

下表來自[共同漏報與交換報告](../reports/stage4/handover_common_misses.json)。只合計三個互不重複的開發月；九個歷史phase仍逐一保留原成熟截止。

| 開發月 | 實際延遲 | 三模型全漏 | 三模型全抓到 | 只有部分模型抓到 |
| --- | ---: | ---: | ---: | ---: |
| 2017-12 | 446 | 355 | 42 | 49 |
| 2018-02 | 890 | 667 | 118 | 105 |
| 2018-04 | 306 | 188 | 85 | 33 |
| 合計 | 1,642 | 1,210 | 245 | 187 |

1,210張占全部延遲73.69%；只有187張在三個模型之間出現抓到／漏掉的分歧。這表示觀察不能只停在四月幾張已知漏報的來回交換，也不能以微小淨改善宣稱已解決共同弱點。這裡的「三模型」僅指三個固定排序對照，不是全專案78個候選。

### 大部分共同漏報不只差一個名額

以下對每張共同漏報，取三模型中最接近前段的完整日排名；這是回溯描述，不是可部署的混合分數。

| 最接近的排名層 | 共同漏報數 |
| --- | ---: |
| 10–20% | 279 |
| 20–50% | 541 |
| 50%之後 | 390 |

另以該日排名減提醒容量計算，僅46張最接近時差1–3個位置，78張差4–10個，1,086張差超過10個。各日訂單量不同，名次距離與百分位是兩個視角，不能相加。不能直接將279張納入提醒，或把三者提醒聯集當成每日10%策略。

### 路線、承諾與歷史支持的共同弱點

| 開發月合計路線 | 該路線實際延遲 | 共同漏報 | 占該路線延遲 |
| --- | ---: | ---: | ---: |
| SP→RJ | 409 | 240 | 58.68% |
| SP→SP | 239 | 195 | 81.59% |
| SP→MG | 84 | 78 | 92.86% |
| SP→RS | 72 | 69 | 95.83% |
| SP→SC | 57 | 47 | 82.46% |

SP→RJ的共同漏報張數最多，但SP→SP與其他路線也有明顯弱點。承諾22–30天的915張延遲有684張共同漏報，31+組300張有260張；這裡31+仍代表`estimated_delivery_days > 30`。路線與承諾是重疊切法，不把它們相加當不同訂單。

共同漏報中1,063張已有至少五筆交運歷史，該組共有1,434張延遲，共同漏報率74.13%；0筆組為34／50＝68.00%，1–4筆組為113／158＝71.52%。大組的張數也受分母影響，不能把共同漏報都歸因於交運歷史不足，或直接依五筆門檻混模型。

### 排名交換保留補抓與新增漏報

三個開發月相對101欄，102欄補抓32張、失去41張，104欄補抓73張、失去75張；102相對104欄補抓73張、失去80張。三者每月仍遵守同一完整日容量，變動只是在既有名額下重新排序。報告保留全部12phase、三組兩兩對照、路線與每日容量記帳，並逐值對齊前輪兩組對照，不產生新的模型成績。

### 可回溯兩個待交運代理，但尚未證明能改善辨識

[核准訊號盤點報告](../reports/stage4/approval_signal_inventory.json)按事前固定契約，從原始訂單與品項重建70,844筆查詢的兩個代理值。主賣家依原有最高品項單價`price`規則決定，同價按品項序號；這仍假設靜態品項與主賣家映射在核准時可知，缺少能直接證明當時版本的時間紀錄。查詢母體截止2018-05-01以前，沒有對原保留測試查詢。

| 訊號／資訊 | 核准時點可用程度 | 本輪處理 |
| --- | --- | --- |
| 主賣家近90天未觀測交運待件件數 | 依較早核准與嚴格早於查詢的事件可回溯，受取消及登錄時間缺漏限制 | 70,844筆皆可計數；已知賣家沒有待件記0，不當缺值 |
| 上述待件核准時齡p90 | 有待件時可回溯；不需等本單未來交運 | 45,089筆有值（63.65%），25,755筆無待件而留空；1筆待件即可計算 |
| 已完成交運事件數／耗時p50、p90 | 歷史事件可用，已在102／104欄測過 | 沿用原模型，沒有當作新增訊號 |
| 本單交運、送達、最終狀態、評論 | 通常在核准後才知道，最終狀態也缺轉換時間 | 不當核准輸入，不以未來狀態篩掉歷史待件 |
| 取消、事件入庫與品項修改時間 | 現有CSV缺時鐘或版本 | 無法確認事件未登錄是否代表實體未交運 |
| 承運商、物流掃描、庫存、人力、即時天氣與交通 | 現有CSV無資料 | 需要另接來源與可用時間，不能由本輪報告推定 |

件數採缺賣家／0／1–4／5–19／至少20筆分箱；時齡採缺賣家／無待件／至多24小時／24–72／72–168／超過168小時，沒有搜尋最佳門檻。70,844筆都能對上主賣家，不表示缺賣家保護可省略。下表只看三模型共同漏報；百分比的分母是當月共同漏報數。

| 開發月 | 共同漏報 | 有待件、時齡可算 | 待件件數中位數 | 時齡p90特徵的中位數（小時） |
| --- | ---: | ---: | ---: | ---: |
| 2017-12 | 355 | 272（76.62%） | 3 | 92.64 |
| 2018-02 | 667 | 480（71.96%） | 2 | 70.37 |
| 2018-04 | 188 | 110（58.51%） | 1 | 69.30 |

每張訂單先算其主賣家待件時齡p90，再對該月有值的訂單取中位數；不是把全體原始待件混在一起計算p90。其他已知延遲的待件件數中位數也是3／2／1，單看中位數尚無法區分哪些會被漏掉。時齡特徵也有重疊：共同漏報的中位數雖高於準時組，二月卻低於其他延遲；三個月準時組的該特徵p90均比共同漏報組更高。不能先設定「件數多／時齡長就提醒」並宣稱有效。

四月188張共同漏報中78張沒有這類待件；其餘110張內87張時齡p90不超過168小時。這個訊號無法單獨解釋全部共同漏報。由答案切分的分布是回溯診斷，也不代表特徵和漏報的因果關係。

### 下一次只測件數，時齡留待另輪消融

建議下一次保持核准時點、L2＝100、topk10、歷史成熟時鐘與完整日10%預算，以原101欄為對照，只加入`seller_unobserved_handover_pending_count_90d`一欄。它描述「尚未觀測交運的待件」，與先前102欄的「已完成交運事件數」不同，也不同於101欄包含在途件的未送達待件。

仍只依原歷史規則決定是否改選，再完整回報各開發月、共同漏報路線、補抓及新增漏報；不能按已知結果混模型或補發額外名額。`seller_unobserved_handover_pending_age_p90_hours_90d`另輪單獨消融，以免混淆件數與時齡效果。本輪只完成盤點，未把兩個代理加入任何模型，尚未得到召回改善證據，也未改變研究主方案。

## 重現方式

使用專案`.venv/`與前輪保留的本機資料、快取及模型檔；本輪不新增套件或MySQL操作。原始資料、模型、候選逐筆數值與執行證明留在Git忽略路徑，GitHub只保存程式、文件、Notebook與聚合報告。

```powershell
.\.venv\Scripts\python.exe scripts\diagnose_handover_common_misses.py
.\.venv\Scripts\python.exe scripts\audit_approval_signals.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

共同漏報腳本需前輪主報告、既有診斷、`handover_history.json`、`handover_count_specification.json`、`backlog_changes.json`、137欄特徵、192,168列分數、七張原始表，以及24份月份模型與3份研究artifact的原檔以核對雜湊，但不載入模型。訊號腳本另需既有`logistics_availability.json`並核對相同原始表清單，實際重建只讀訂單與品項需要的欄位；其契約可從腳本的固定內容重建，不必上傳本機事前快照。若需保存逐筆診斷，可加`--cache-output .runtime\verification\approval-signal-values.csv`；該路徑與原始資料、模型一樣由Git忽略。
